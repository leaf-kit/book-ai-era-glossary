# 42장 평가와 벤치마크

<sub>8부 만들고 운영하기 · 표제어 75개 · 도해 3개</sub>

> **여는 지도** — 이 장의 낱말 일흔다섯. 무엇을 어떻게 재는가로 일곱 무리

이 장은 좋아졌는지 판단하는 절차를 다룬다. 15장의 지표가 여기서 다시 나오는데, 조건이 하나 달라졌다. 정답이 하나로 정해지지 않는다.

분류 문제는 맞고 틀림이 분명하다. 문장을 만드는 문제는 그렇지 않다. 같은 뜻을 다른 말로 적어도 맞고, 형식은 맞는데 내용이 틀릴 수도 있고, 사람마다 어느 쪽이 나은지 판단이 갈린다. 이 하나가 이 장 전체를 어렵게 만든다.

그래도 재야 한다. 안 재면 바꿀 때마다 느낌으로 판단하게 되고, 느낌은 마지막에 본 사례에 좌우된다. 작은 평가 집합이라도 있으면 방향은 알 수 있다. 없는 것보다 부실한 것이 낫다는 것이 이 장의 실무적 결론이다.

## 한눈에 보기

| 무리 | 무엇을 다루나 | 어디서 다시 쓰나 |
|---|---|---|
| 평가 집합 | 무엇으로 잴 것인가 | 31장 프롬프트 평가 |
| 채점 방식 | 누가 어떻게 매기나 | 26장 선호 |

| 에이전트 평가 | 여러 걸음을 재는 문제 | 7부 전체 |
| 함정 | 무엇이 결과를 망치나 | 10장 굿하트 |


## 표제어

### 무엇으로 잴 것인가

#### 골든셋

<sub>Golden Set</sub>

**정답이나 기준이 정해진 평가용 사례 묶음.**

<sub>관련어 평가 집합, 회귀 평가, 실패 사례 수집, 시험 집합(12장)</sub>

- **평가 집합** `Evaluation Set` — 평가에 쓰는 사례 묶음. 골든셋과 거의 같은 뜻으로 쓰인다.
- **사례 수집** `Case Collection` — 실제 사용에서 평가에 쓸 만한 사례를 모으는 일. 자동으로 쌓이게 만들어 두면 유지가 쉽다.
- **실패 사례** `Failure Case` — 잘못 답한 사례. 평가 집합에 반드시 들어가야 하는 것들이다.
- **난이도 분포** `Difficulty Distribution` — 쉬운 것과 어려운 것의 비율. 쉬운 것만 있으면 변별이 안 되고 어려운 것만 있으면 개선이 안 보인다.
- **범주 나누기** `Category Breakdown` — 사례를 종류별로 나눠 각각 점수를 보는 것. 전체 평균이 같아도 어느 종류가 나빠졌는지 보인다. 15장의 슬라이스 평가다.
- **합성 평가 데이터** `Synthetic Eval Data` — 모델로 만들어 낸 평가 사례. 빠르게 채울 수 있고 실제 요청과 성격이 달라 그것만으로는 부족하다.
- **평가 집합 유출** `Eval Set Leakage` — 평가 사례가 프롬프트나 학습에 들어간 상태. 점수가 오르고 실제는 안 좋아진다.

### 누가 어떻게 채점하나

**채점 방식 다섯**

| 방식 | 어떻게 하나 | 장점 | 한계 |

|---|---|---|---|

| 정확 일치 | 정답과 같은지 본다 | 싸고 확실하다 | 표현이 다르면 틀림 |

| 규칙 검사 | 형식과 조건을 확인 | 자동화된다 | 내용은 못 본다 |

| 실행 검증 | 코드를 돌려 본다 | 확실하다 | 되는 과제에만 |

| 모델 판정 | 다른 모델이 채점 | 싸고 빠르다 | 편향이 있다 |

| 사람 평가 | 사람이 읽고 매긴다 | 가장 믿을 만하다 | 비싸고 느리다 |

위에서부터 쓸 수 있으면 쓰는 것이 순서다.
형식과 필수 항목은 규칙으로 검사하고, 코드는 돌려 보고,
남는 부분만 모델이나 사람에게 맡긴다.
전부를 모델 판정에 맡기는 구성이 흔한데, 싼 대신 확인이 안 된 채로 돌아간다.

#### LLM 판정 〔신조〕

<sub>LLM-as-a-Judge</sub>

**모델에게 다른 모델의 답을 채점하게 하는 방식.**

갈리는 자리 — 어느 정도 믿을 수 있는지에 대한 결과가 과제마다 크게 다르다

생긴 때 — 2023년 이후 널리 쓰인다

<sub>관련어 판정 편향, 채점 기준, 사람 평가(15장), 쌍대 비교(15장)</sub>

- **채점 기준** `Rubric` — 무엇을 보고 점수를 매길지 적어 둔 기준표. 항목을 나눠 적을수록 판정이 일관된다.
- **판정 편향** `Judge Bias` 〔신조〕 — 채점 모델이 가진 치우침. 길이, 순서, 자기 출력 선호가 알려져 있다. <sub>생긴 때: 2023년 이후 보고된다</sub>
- **순서 편향** `Position Bias` — 두 답을 비교할 때 먼저 나온 쪽을 고르는 경향. 순서를 바꿔 두 번 물어 상쇄한다.
- **자기 선호** `Self-Preference` 〔신조〕 — 채점 모델이 자기와 같은 모델이 만든 답을 좋게 보는 경향. <sub>생긴 때: 2023년 이후 보고된다</sub>
- **판정 검증** `Judge Validation` — 모델 판정이 사람 판단과 얼마나 맞는지 확인하는 절차. 안 하면 무엇을 재는지 모른다.
- **규칙 기반 검사** `Rule-Based Check` — 형식과 필수 항목과 금칙어를 자동으로 확인하는 것. 싸고 확실해서 먼저 돌린다.
- **실행 기반 검증** `Execution-Based Evaluation` — 코드를 돌려 결과로 채점하는 방식. 39장의 코딩 평가가 이것이다.
- **정확 일치** `Exact Match` — 정답 문자열과 같은지 보는 채점. 짧은 답에만 쓸 수 있다.
- **쌍대 비교 (평가)** `Pairwise Evaluation` — 두 결과 중 어느 쪽이 나은지 고르게 하는 방식. 절대 점수보다 일관된다.
- **승률** `Win Rate` — 비교에서 이긴 비율. 기준이 되는 대상이 무엇인지 같이 적어야 뜻이 있다.
- **일관성 확인** `Consistency Check` — 같은 것을 여러 번 채점해 결과가 같은지 보는 것. 채점 자체가 흔들리면 비교가 안 된다.

### 공개 벤치마크

#### 벤치마크 〔유동〕

<sub>Benchmark</sub>

**여러 모델을 같은 조건에서 비교하려고 만든 표준 시험 묶음.**

갈리는 자리 — 점수를 비교할 때 설정을 안 적는 관행이 있어 값이 그대로는 비교가 안 된다

<sub>관련어 오염, 리더보드, MMLU, GPQA, 아레나 평가, 골든셋, 굿하트의 법칙(10장)</sub>

**널리 인용되는 시험들**

| 무엇을 재나 | 자주 나오는 이름 | 어떤 시험인가 |

|---|---|---|

| 넓은 지식 | MMLU, MMLU-Pro | 쉰일곱 분야의 객관식 문제. 앞의 것은 점수가 위쪽에 몰려 변별이 잘 안 되게 되었고, 뒤의 것은 보기를 늘려 어렵게 만든 판이다 |

| 어려운 추론 | GPQA | 대학원 수준 과학 문제. 검색해서는 답이 잘 안 나오게 고른 것이 특징이다 |

| 수학 | GSM8K, MATH, AIME | 차례로 여러 단계 서술형 산수, 경시대회 수준 문제, 고교 경시대회 문제를 그대로 가져다 쓴 것 |

| 코드 | HumanEval, MBPP, LiveCodeBench | 앞의 둘은 함수 하나를 적어 단위 시험을 통과시키는 것. 뒤의 것은 새로 출제된 문제만 써서 오염을 피하려는 시도다 |

| 상식과 함정 | HellaSwag, TruthfulQA, WinoGrande | 차례로 이어질 문장 고르기, 흔한 오해를 따라가는지, 대명사가 무엇을 가리키는지 |

| 긴 문맥 | 건초더미 시험, RULER | 긴 입력 안에서 필요한 것을 찾아내고 이어 붙이는지. 앞의 것은 24장에 있다 |

| 그림까지 | MMMU, DocVQA, ChartQA | 차례로 대학 수준 도표 문제, 문서 이미지 질의응답, 그래프 읽기 |

| 사람 선호 | 아레나 평가, MT-Bench | 앞은 사람이 두 답 중 고른 결과를 모은 것, 뒤는 여러 차례 대화를 모델이 채점한 것 |

| 한국어 | KMMLU | 한국어로 된 지식 시험. 영어 쪽만큼 촘촘하지 않다 |

이름을 외울 필요는 없고 무엇을 재는 시험인지만 알면 된다.
어느 것이든 점수 하나로 모델을 말할 수 없다. 몇 번 시도했는지와 어떻게 채점했는지가 같이 적혀야 하고,
널리 쓰인 시험일수록 오염되었을 가능성이 크다.
발표 자료에서 이름을 보면 그 시험이 재는 것이 지금 내 과제와 얼마나 닮았는지를 먼저 본다.

- **MMLU** `Massive Multitask Language Understanding` — 쉰일곱 분야의 객관식 문제로 넓은 지식을 재는 시험. 오랫동안 기본 지표로 인용되었고, 상위 점수가 몰리면서 보기를 늘린 더 어려운 판이 따로 나왔다.
- **GPQA** `Graduate-Level Google-Proof Q&A` 〔신조〕 — 생물과 물리와 화학의 대학원 수준 문제. 검색으로는 답을 찾기 어렵게 고른 것이 이름에 들어 있고, 그래서 외운 지식과 따져 보는 능력을 가르려는 시험이다. <sub>생긴 때: 2023년 무렵 나왔다</sub>
- **GSM8K** `Grade School Math 8K` — 여러 단계를 거쳐야 답이 나오는 서술형 산수 문제 묶음. 계산 자체는 쉬운데 단계를 놓치면 틀려서, 30장의 사고 사슬 효과를 보이는 데 오래 쓰였다.
- **HumanEval** `HumanEval` — 설명을 주고 파이썬 함수 하나를 적게 한 뒤 미리 만들어 둔 단위 시험으로 채점하는 시험. 코드 평가의 오래된 기준선이고, 함수 하나 크기라 실제 개발과는 거리가 있다.
- **MMMU** `Massive Multi-discipline Multimodal Understanding` 〔신조〕 — 그림과 도표가 섞인 대학 수준 문제로 멀티모달 능력을 재는 시험. 글만 읽어서는 못 풀게 만든 것이 특징이다. <sub>생긴 때: 2023년 무렵 나왔다</sub>
- **아레나 평가** `Arena-Style Evaluation` 〔신조〕 — 같은 질문에 두 모델이 답하게 하고 사람이 어느 쪽이 나은지 골라, 그 결과를 모아 순위를 매기는 방식. 실제 사용 느낌에 가깝고, 말투와 길이에 좌우되며 어떤 사람이 투표했는지에 따라 결과가 달라진다. <sub>생긴 때: 2023년 무렵부터 널리 쓰인다</sub>
- **한국어 벤치마크** `Korean Benchmark` 〔유동〕 — 한국어 능력을 재는 시험 묶음. KMMLU처럼 한국어로 된 지식 시험이 나와 있고, 영어를 옮겨 만든 것과 한국의 맥락에서 새로 만든 것이 섞여 있다. 무엇을 한국어 능력으로 볼지가 시험마다 달라 점수를 그대로 견주기 어렵다.
- **리더보드** `Leaderboard` 〔유동〕 — 여러 모델의 점수를 순위로 늘어놓은 표. 순위가 자주 바뀌고, 무엇으로 잰 순위인지가 늘 따라붙어야 한다.
- **오염** `Contamination` — 평가 문제가 학습 데이터에 들어간 상태. 점수가 부풀려지고 발견이 어렵다. 25장에서 정의했다.
- **오염 탐지** `Contamination Detection` — 학습 데이터에 평가 문제가 들어갔는지 확인하려는 시도. 학습 데이터가 비공개면 사실상 확인이 안 된다.
- **비공개 평가** `Held-Out Benchmark` — 문제를 공개하지 않고 채점만 해 주는 방식. 오염을 막는 방법이고 검증이 어려워진다.
- **동적 벤치마크** `Dynamic Benchmark` 〔신조〕 — 문제를 계속 새로 만들어 오염을 피하려는 방식. 시점마다 난이도가 달라 비교가 까다롭다. <sub>생긴 때: 2023년 이후 시도된다</sub>
- **평가 설정** `Evaluation Setting` — 몇 번 시도했는지, 어떤 프롬프트를 썼는지, 어떻게 채점했는지. 이것을 안 적은 점수는 비교가 안 된다.
- **여러 번 시도** `Pass@k` — k번 시도해서 하나라도 맞으면 성공으로 세는 방식. 한 번에 맞아야 하는 것과 크게 다르므로 구별해 적어야 한다.
- **사람 선호 순위** `Human Preference Ranking` — 사람들이 두 답을 비교해 고른 결과를 모아 매긴 순위. 실제 사용 느낌과 가깝고 취향과 말투에 좌우된다.
- **과제별 벤치마크** `Domain Benchmark` — 특정 분야에 맞춘 시험 묶음. 일반 벤치마크보다 실제 쓸모를 잘 나타낸다.

### 언제 재는가

- **회귀 평가** `Regression Evaluation` — 바꾸기 전에 되던 것이 안 깨졌는지 확인하는 절차. <sub>관련어 골든셋, 배포 전 관문, 회귀 테스트(7장), 능력 회귀(26장)</sub>
- **배포 전 관문** `Pre-Deployment Gate` — 정해진 기준을 통과해야 내보내게 하는 절차. 통과 기준을 미리 정해 둬야 논쟁이 안 생긴다.
- **개발 중 평가** `Development Evaluation` — 만드는 동안 빠르게 돌리는 평가. 몇 분 안에 끝나야 실제로 쓰인다.
- **운영 중 평가** `Online Evaluation` — 실제 사용자 요청에서 재는 것. 오프라인 평가로 안 잡히는 문제를 잡는다.
- **오프라인 평가** `Offline Evaluation` — 정해진 집합으로 미리 재는 것. 통제가 되고 실제와 다를 수 있다.
- **A/B 테스트** `A/B Test` — 실제 사용자를 나눠 두 방식을 동시에 써 보고 결과를 비교하는 것. <sub>관련어 인과(10장), 다중 비교(10장), 온라인 지표, 통계적 유의성(15장)</sub>
- **온라인 지표** `Online Metric` — 실제 사용에서 관찰되는 값. 재질문율, 이어 간 비율, 이탈률 같은 것들이다.
- **대리 지표** `Proxy Metric` — 진짜 목표를 직접 못 재서 대신 보는 값. 이 값을 목표로 삼으면 굿하트 문제가 생긴다.
- **사용자 피드백** `User Feedback` — 좋아요와 싫어요 같은 직접 신호. 응답률이 낮고 치우쳐 있어 그것만으로는 부족하다. 45장에서 다시 나온다.
- **암묵 신호** `Implicit Signal` — 복사, 재질문, 편집 같은 행동에서 읽는 신호. 직접 물어보는 것보다 양이 많다.
- **점진 노출** `Staged Rollout` — 일부에게만 먼저 보이고 지켜보는 것. 41장의 점진 전환과 같은 절차다.

### 에이전트를 평가하기

#### 에이전트 평가 〔신조〕

<sub>Agent Evaluation</sub>

**여러 걸음을 도는 시스템이 일을 해냈는지 재는 일.**

생긴 때 — 2024년 이후 문제로 다뤄진다

<sub>관련어 과업 성공률(40장), 궤적(35장), GAIA, SWE-bench(39장), 안전 위반, 트레이스(43장에서 다룬다)</sub>

**에이전트 벤치마크**

| 이름 | 어떤 환경인가 | 무엇을 요구하나 |

|---|---|---|

| SWE-bench | 실제 저장소에 올라온 이슈 | 코드를 고쳐 원래 있던 시험을 통과시킨다 |

| WebArena | 실제처럼 만들어 둔 웹사이트 | 여러 화면을 오가며 주문과 조회 같은 일을 끝낸다 |

| OSWorld | 진짜 운영체제 화면 | 파일과 프로그램을 직접 다뤄 일을 끝낸다 |

| GAIA | 도구와 웹을 쓸 수 있는 일반 과업 | 사람에게는 쉽고 도구 없이는 못 푸는 질문에 답한다 |

| AgentBench | 여러 환경을 한데 모은 것 | 환경마다 다른 방식으로 일을 끝낸다 |

| tau-bench | 규칙이 정해진 고객 응대 | 사용자와 주고받으며 정책을 안 어기고 처리한다 |

| MLE-bench | 데이터가 주어진 기계학습 과제 | 스스로 모델을 만들어 점수를 낸다 |

공통점은 환경을 만드는 비용이다.
일반 시험은 문제와 정답만 있으면 되는데, 여기서는 매번 같은 상태에서 시작하는 환경이 있어야 한다.
그래서 개수가 적고 새로 만들기 어렵다.
그리고 여기서 나온 점수는 모델만의 점수가 아니라 하네스까지 합한 점수다.
같은 모델이 다른 하네스에서 다른 점수를 받는다.
앞의 셋은 39장과 40장에서 표제어로 다시 다룬다.

- **GAIA** `General AI Assistant Benchmark` 〔신조〕 — 사람에게는 어렵지 않은데 도구 없이는 풀 수 없는 질문을 모은 시험. 웹을 뒤지고 파일을 열고 계산해야 답이 나와서, 도구를 실제로 쓸 줄 아는지를 가른다. <sub>생긴 때: 2023년 무렵 나왔다</sub>
- **효율 지표** `Efficiency Metric` — 걸음 수와 토큰 수와 시간. 같은 일을 얼마나 싸게 했는지 재는 축이다.
- **안전 위반율** `Safety Violation Rate` — 하면 안 될 조작을 한 비율. 성공률과 반드시 나눠 봐야 한다.
- **시험 환경** `Evaluation Environment` — 매번 같은 상태에서 시작할 수 있게 고정한 환경. 재현 가능한 평가의 전제다.
- **궤적 채점** `Trajectory Scoring` 〔신조〕 — 결과만이 아니라 진행 과정을 함께 채점하는 것. 어느 걸음이 불필요했는지 볼 수 있다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **도구 사용 정확도** `Tool Use Accuracy` — 올바른 도구를 올바른 인자로 불렀는지의 비율. 36장의 실패를 잡는 지표다.
- **중간 단계 평가** `Step-Level Evaluation` — 각 걸음이 맞았는지 따로 재는 것. 끝에서만 재면 어디서 틀렸는지 모른다.

### 무엇이 결과를 망치나

**평가가 실제와 어긋나는 여섯 가지**

| 함정 | 무슨 일이 생기나 | 대책 |

|---|---|---|

| 오염 | 점수만 오른다 | 자체 집합, 비공개 평가 |

| 평가 집합 과적합 | 그 집합에만 맞춰진다 | 주기적으로 갱신 |

| 쉬운 사례 편중 | 다 통과해 변별이 안 된다 | 난이도 분포 확인 |

| 판정 편향 | 특정 스타일이 유리해진다 | 판정 검증, 순서 교차 |

| 표본 부족 | 우연을 개선으로 읽는다 | 구간 추정, 표본 확대 |

| 지표 조작 | 지표만 오르고 실제는 안 좋아진다 | 여러 축을 함께 본다 |

마지막 줄이 근본이다. 하나의 숫자를 목표로 삼는 순간
그 숫자를 올리는 방향으로 모든 것이 기운다.
품질과 비용과 지연과 안전을 함께 보는 것이 유일한 방어다.

- **평가 과적합** `Overfitting to Eval` — 평가 집합에만 맞춰지는 것. 같은 집합을 오래 쓰면 반드시 생긴다.
- **지표 조작** `Metric Gaming` — 지표만 올리고 실제는 안 좋아지는 것. 26장의 보상 해킹과 같은 현상이다.
- **표본 부족** `Insufficient Sample` — 사례가 적어 차이가 우연인지 알 수 없는 상태. 구간을 같이 적으면 드러난다.
- **불확실성 표기** `Confidence Interval Reporting` — 점수에 흔들림 구간을 같이 적는 것. 안 적으면 소수점 차이를 개선으로 읽게 된다.
- **설정 미기재** `Undisclosed Setting` — 어떤 조건에서 잰 값인지 안 적는 것. 비교를 무의미하게 만든다.
- **체리 피킹** `Cherry-Picking` — 잘 나온 사례만 골라 보여 주는 것. 여러 번 돌려 좋은 것만 남기는 것도 같다.
- **기준선 누락** `Missing Baseline` — 비교 대상 없이 점수만 제시하는 것. 좋은지 나쁜지 판단할 근거가 없다.

### 평가 체계를 만드는 일

- **평가 파이프라인** `Evaluation Pipeline` — 평가를 자동으로 돌리고 결과를 기록하는 절차. 손으로 돌리면 안 돌게 된다.
- **평가 기록** `Eval Tracking` — 어느 설정에서 어떤 점수가 나왔는지 남기는 일. 없으면 무엇 때문에 좋아졌는지 못 찾는다.
- **평가 비용** `Evaluation Cost` — 평가를 돌리는 데 드는 돈과 시간. 모델 판정을 쓰면 이것도 무시할 수 없다.
- **평가 카드** `Eval Card` 〔신조〕 — 무엇을 어떻게 쟀는지 정리해 붙이는 문서. 49장의 모델 카드와 같은 발상이다. <sub>생긴 때: 2023년 이후 쓰인다</sub>
- **합격 기준** `Acceptance Threshold` — 어느 정도면 내보내도 되는지의 기준. 미리 정해 두지 않으면 결과를 보고 기준을 맞추게 된다.
- **다축 평가** `Multi-Dimensional Evaluation` — 품질과 비용과 지연과 안전을 함께 보는 것. 하나만 보면 나머지가 나빠진다.
- **사람 검토 표본** `Human Review Sample` — 자동 평가 결과 중 일부를 사람이 직접 확인하는 것. 자동 평가가 어긋나는 것을 잡는 안전장치다.

### 무엇으로 재는지도 재야 한다

- **평가 하네스** `Evaluation Harness` 〔신조〕 — 평가를 실제로 돌리는 장치. 문제를 넣고 답을 받아 채점하기까지의 코드 전부. <sub>생긴 때: 2022년 무렵부터 쓰인다 · 관련어 하네스(35장), 평가 설정, 하네스 편차, 재현 가능한 환경(40장)</sub>
- **하네스 편차** `Harness Variance` 〔신조〕 — 모델은 그대로인데 평가 장치가 달라져 점수가 달라지는 것. <sub>생긴 때: 2024년 이후 문제로 다뤄진다 · 관련어 평가 하네스, 에이전트 평가, 평가 설정, 벤치마크</sub>
- **골든 트레이스** `Golden Trace` 〔신조〕 — 좋은 진행 기록을 정답 삼아 모아 둔 것. 결과만이 아니라 어떤 경로로 갔는지까지 비교할 때 쓴다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **하네스 고정** `Harness Pinning` 〔신조〕 — 평가 장치의 판본을 고정해 두는 일. 안 하면 지난달 점수와 이번 달 점수가 비교되지 않는다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **동일 조건 비교** `Apples-to-Apples` — 같은 하네스와 같은 설정으로 두 모델을 재는 것. 이것이 아니면 순위에 뜻이 없다.

## 자주 헷갈리는 짝

- **벤치마크와 골든셋** 같은 점은 둘 다 평가용 사례 묶음이라는 것.
다른 점은 대상이다. 앞은 모델을 비교하고 뒤는 내 시스템을 확인한다.
- **오프라인 평가와 A/B 테스트** 같은 점은 둘 다 좋아졌는지 본다는 것.
다른 점은 실제 사용자가 있는가다. 앞으로 방향을 잡고 뒤로 확인한다.
- **LLM 판정과 사람 평가** 같은 점은 둘 다 정답 없는 답을 채점한다는 것.
다른 점은 비용과 신뢰다. 앞을 쓰려면 뒤와 맞는지 먼저 확인해야 한다.
- **오염과 평가 과적합** 같은 점은 둘 다 점수를 부풀린다는 것.
다른 점은 경로다. 앞은 학습에 들어갔고 뒤는 반복해 맞췄다.
- **회귀 평가와 벤치마크** 같은 점은 둘 다 정해진 집합으로 잰다는 것.
다른 점은 목적이다. 앞은 안 깨졌는지 보고 뒤는 얼마나 좋은지 본다.
- **평가 하네스와 에이전트 하네스** 같은 낱말이고 감싸는 대상이 다르다.
앞은 시험을 돌리는 장치이고 뒤는 35장의 일을 하는 장치다.
에이전트를 평가할 때는 둘이 겹쳐서 점수가 어느 쪽의 것인지 흐려진다.
- **골든셋과 골든 트레이스** 같은 점은 둘 다 정답으로 삼는 기록이라는 것.
다른 점은 무엇을 담는가다. 앞은 답이고 뒤는 거기까지 간 경로다.

## 지금 움직이는 것

공개 벤치마크의 값이 떨어지고 자체 평가의 값이 오르는 흐름이 뚜렷하다. 오염과 최적화 때문에 공개 점수가 실제 쓸모를 덜 나타내게 되었고, 그래서 각자 자기 과제에 맞는 집합을 만드는 쪽으로 옮겨 갔다. 동시에 에이전트 평가가 새 과제로 올라왔다. 여러 걸음을 재려면 환경을 고정해야 하는데 그 환경을 만드는 비용이 크다.
