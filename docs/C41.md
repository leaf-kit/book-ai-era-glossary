# 41장 서빙과 추론 인프라

<sub>8부 만들고 운영하기 · 표제어 56개 · 도해 4개</sub>

> **여는 지도** — 이 장의 낱말 쉰여섯. 요청 하나가 답이 되어 나가기까지 여섯 자리

이 장은 만들어진 모델을 실제로 돌려 요청에 답하게 하는 장치를 다룬다. 8부의 첫 장이고, 4장의 네트워크와 2장의 하드웨어가 여기서 다시 만난다.

일반 웹 서비스와 다른 점이 셋이다. 요청 하나가 수 초에서 수십 초를 잡고, 응답이 한 번에 나오지 않고 조금씩 흘러나오고, 가속기 메모리가 동시에 받을 수 있는 요청 수를 정한다. 기존 서버 운영의 상식이 이 셋 때문에 조금씩 안 맞는다.

24장에서 나눈 두 단계가 여기서 설계의 중심이 된다. 입력을 읽는 단계는 가속기를 꽉 채우고, 답을 만드는 단계는 가속기가 논다. 그 비대칭을 어떻게 다루느냐가 이 장의 절반이다.

## 표제어

### 앞단에서 하는 일

#### 서빙

<sub>Serving</sub>

**학습된 모델을 실제로 돌려 요청에 답하게 하는 일과 그 구조.**

<sub>관련어 게이트웨이, 배칭, 처리량, 추론(27장)</sub>

- **게이트웨이** `Gateway` — 모델 호출 앞에 서서 인증과 제한과 라우팅과 기록을 처리하는 층. <sub>관련어 속도 제한(4장), 라우팅, 폴백, 사용량 집계</sub>
- **속도 제한 (모델)** `Rate Limiting` — 분당 요청 수나 분당 토큰 수로 거는 제한. 토큰 기준이 실제 부하와 맞아 널리 쓰인다.
- **할당량** `Quota` — 일정 기간에 쓸 수 있는 총량. 사용자나 팀 단위로 나눠 준다.
- **사용량 집계** `Usage Metering` — 누가 얼마나 썼는지 세는 일. 비용을 나누고 이상한 사용을 잡는 근거가 된다.
- **인증 (모델 호출)** `API Authentication` — 누가 부르는지 확인하는 절차. 9장의 열쇠 관리가 여기서 그대로 필요하다.
- **요청 큐** `Request Queue` — 처리를 기다리는 요청들의 줄. 길이가 지연을 정하고, 너무 길면 거절하는 편이 낫다.
- **부하 차단** `Load Shedding` — 감당 못 할 때 일부 요청을 미리 거절하는 것. 다 받아 다 느려지는 것보다 낫다.
- **우선순위 큐** `Priority Queue` — 급한 요청을 먼저 처리하는 구조. 대화형 요청과 일괄 처리 요청을 나눠 다룬다.

### 묶어서 처리하기

#### 배칭

<sub>Batching</sub>

**여러 요청을 묶어 한 번에 처리하는 것.**

갈리는 자리 — 학습에서 데이터를 묶는 것과 서빙에서 요청을 묶는 것이 같은 낱말이다

<sub>관련어 연속 배칭, 처리량, 메모리 대역폭(2장), 배치(13장)</sub>

- **연속 배칭** `Continuous Batching` — 끝난 요청을 빼고 새 요청을 바로 채워 넣는 방식. 자리가 안 놀아 처리량이 크게 오른다.
- **정적 배칭** `Static Batching` — 묶음을 정해 놓고 다 끝날 때까지 기다리는 방식. 단순하고 자리가 논다.
- **배치 크기 (서빙)** `Serving Batch Size` — 동시에 처리하는 요청 수. 메모리가 이 값을 정한다.
- **프리필 디코드 분리** `Prefill-Decode Disaggregation` 〔신조〕 — 입력을 읽는 단계와 답을 만드는 단계를 다른 기계에 맡기는 구성. 두 단계의 병목이 달라서 나온 설계다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **스케줄링 (서빙)** `Serving Scheduler` — 어느 요청을 언제 처리할지 정하는 부분. 3장의 스케줄러와 같은 문제를 다룬다.
- **선점 (서빙)** `Preemption` — 진행 중인 요청을 잠시 밀어내고 다른 것을 처리하는 것. 밀어낸 요청의 캐시를 어떻게 할지가 문제가 된다.
- **공정성 (대기열)** `Fairness` — 한 사용자가 자원을 독차지하지 않게 하는 것. 긴 요청 하나가 짧은 요청 여럿을 막는 상황을 다룬다.

### 메모리를 관리하기

- **KV 캐시 관리** `KV Cache Management` — 요청마다 쌓이는 키와 값 저장 공간을 배분하고 회수하는 일. <sub>관련어 페이지드 어텐션(24장), KV 캐시(24장), 배칭, 접두 캐시</sub>
- **접두 캐시** `Prefix Caching` — 여러 요청이 같은 앞부분을 공유할 때 그 부분의 캐시를 재사용하는 것. 시스템 프롬프트가 길수록 이득이 크다.
- **캐시 적중** `Cache Hit` — 재사용에 성공한 경우. 32장의 캐시 정렬이 이 비율을 올린다.
- **메모리 조각남** `Memory Fragmentation` — 쓸 수 있는 메모리가 흩어져 큰 덩어리를 못 잡는 상태. 페이지 방식이 이것을 없앤다.
- **모델 적재** `Model Loading` — 가중치를 가속기 메모리에 올리는 일. 큰 모델은 이것만 수십 초가 걸려 자주 띄우고 내릴 수가 없다.
- **상주 모델** `Warm Model` — 미리 올려 두고 대기하는 모델. 8장의 콜드 스타트를 없애고 안 쓰는 동안에도 자원을 잡는다.
- **다중 모델 서빙** `Multi-Model Serving` — 한 서버에서 여러 모델을 돌리는 것. 28장의 어댑터 교체가 이 자리에서 쓰인다.
- **어댑터 서빙** `Adapter Serving` 〔신조〕 — 본체 하나에 용도별 어댑터를 붙여 여러 용도를 한 서버에서 처리하는 방식. <sub>생긴 때: 2023년 이후 쓰인다</sub>

### 어느 모델로 보낼까

**라우팅의 다섯 가지 기준**

| 기준 | 어떻게 나누나 | 얻는 것 | 위험 |

|---|---|---|---|

| 난이도 | 쉬우면 작은 모델 | 비용 절감 | 판별이 틀림 |

| 과제 종류 | 코드는 이쪽, 번역은 저쪽 | 품질 | 분류 비용 |

| 비용 예산 | 남은 예산에 맞춰 | 예측 가능성 | 품질 변동 |

| 지연 요구 | 급하면 빠른 모델 | 체감 속도 | 품질 변동 |

| 가용성 | 죽었으면 다른 곳으로 | 안정성 | 품질이 달라짐 |

첫 줄이 비용에 가장 큰 영향을 준다.
쉬운 요청이 대부분인 서비스에서 작은 모델로 나누면 요금이 크게 준다.
다만 난이도 판별이 틀리면 어려운 것을 작은 모델이 받아 나쁜 답이 나간다.
그 비율을 재고 문턱을 조정하는 것이 실무다.

- **라우팅 (모델)** `Model Routing` — 요청을 어느 모델로 보낼지 정하는 일. 25장의 전문가 라우터, 38장의 오케스트레이터와 이름이 겹친다.
- **폴백** `Fallback` — 실패하거나 제한에 걸리면 다른 모델이나 다른 제공자로 넘기는 것. 품질이 달라진다는 것을 알고 써야 한다.
- **다중 제공자** `Multi-Provider` — 여러 회사의 모델을 함께 쓰는 구성. 안정성이 오르고 프롬프트를 여러 벌 관리해야 한다.
- **지역 배치** `Regional Deployment` — 사용자 가까운 리전에 배치하는 것. 지연이 줄고 데이터가 그 지역에 머문다는 요건도 만족한다.
- **데이터 소재** `Data Residency` — 데이터가 어느 나라에 머무는지. 규제 때문에 리전 선택이 강제되는 경우가 있다. 49장에서 다시 나온다.

### 내보내기

- **첫 토큰까지** `Time to First Token, TTFT` — 요청을 보내고 첫 글자가 나오기까지의 시간. 체감 속도를 가장 크게 좌우한다. 44장에서 자세히 다룬다.
- **부분 응답** `Partial Response` — 아직 끝나지 않은 상태의 답. 형식이 완성되기 전이라 파싱에 주의가 필요하다.
- **연결 유지** `Connection Management` — 긴 응답 동안 연결을 유지하는 일. 중간 장비의 타임아웃에 걸리지 않게 해야 한다.
- **중단 처리** `Client Disconnect` — 사용자가 중간에 나갔을 때 계산을 멈추는 처리. 안 하면 아무도 안 보는 답을 계속 만든다.
- **배치 API** `Batch API` — 급하지 않은 요청을 모아 나중에 처리하고 싸게 받는 방식. 지연을 내주고 비용을 얻는다.
- **비동기 작업** `Async Job` — 요청을 접수하고 나중에 결과를 가져가게 하는 구성. 오래 걸리는 에이전트 작업에 맞는다.

### 무엇을 지켜보나

**서빙에서 보는 여섯 숫자**

| 숫자 | 무엇을 말하나 | 나빠지면 |

|---|---|---|

| 첫 토큰 지연 | 얼마나 빨리 시작하나 | 대기열이 길다 |

| 토큰당 지연 | 얼마나 빨리 이어지나 | 배치가 크거나 모델이 크다 |

| 처리량 | 초당 몇 토큰을 내나 | 자원이 모자라다 |

| 대기열 길이 | 얼마나 밀려 있나 | 용량 부족 |

| 가속기 사용률 | 얼마나 놀고 있나 | 배칭이 안 된다 |

| 오류율 | 얼마나 실패하나 | 제한이나 장애 |

처음 두 줄이 사용자 경험이고 나머지가 원인 쪽이다.
그리고 전부 평균이 아니라 백분위로 봐야 한다.
평균이 좋은데 열에 하나가 아주 느리면 사용자는 느리다고 느낀다.

- **처리량 (서빙)** `Throughput` — 단위 시간에 처리한 토큰이나 요청의 수. 배칭이 이 값을 크게 올린다.
- **가속기 사용률** `GPU Utilization` 〔유동〕 — 가속기가 노는 시간 없이 일하는 비율. 무엇을 세느냐가 도구마다 달라 값이 다르게 나온다.
- **대기열 길이** `Queue Depth` — 처리를 기다리는 요청 수. 이 값이 첫 토큰 지연의 주된 원인이다.
- **포화** `Saturation` — 자원이 한계에 이른 상태. 여기서부터는 요청이 늘어도 처리량이 안 늘고 지연만 는다.
- **용량 산정** `Capacity Planning` — 얼마나 많은 요청을 받을 수 있는지 계산하는 일. 메모리와 배치 크기와 평균 길이로 정해진다.
- **부하 시험** `Load Testing` — 실제와 비슷한 부하를 걸어 한계를 확인하는 일. 요청 길이 분포를 실제와 맞춰야 뜻이 있다.

### 모델을 바꾸는 일

- **모델 배포** `Model Deployment` — 새 모델이나 새 설정을 운영에 내보내는 일. <sub>관련어 카나리 배포(7장), 롤백 (배포)(7장), 버전 고정, 회귀 평가(42장에서 다룬다)</sub>
- **버전 고정** `Version Pinning` — 특정 모델 판본을 지정해 쓰는 것. 조용한 갱신으로 동작이 바뀌는 것을 막는다.
- **모델 폐기** `Model Deprecation` — 제공자가 옛 모델 지원을 끊는 것. 0장의 지원 중단이 여기서 실제 일정이 된다.
- **그림자 배포** `Shadow Deployment` — 새 모델에 같은 요청을 보내되 결과는 안 쓰고 비교만 하는 방식. 위험 없이 비교할 수 있다.
- **점진 전환** `Gradual Rollout` — 비율을 조금씩 올려 가며 바꾸는 방식. 문제가 보이면 되돌린다.
- **A/B 비교** `A/B Comparison` — 두 모델에 요청을 나눠 보내 결과를 비교하는 것. 42장에서 자세히 다룬다.
- **설정 관리** `Configuration Management` — 온도와 최대 토큰 같은 설정을 어디에 두고 어떻게 바꾸는지. 코드에 박아 두면 바꿀 때마다 배포해야 한다.

### 직접 돌릴 때

- **추론 서버** `Inference Server` — 모델을 올려 두고 요청을 받는 프로그램. 배칭과 캐시 관리가 여기 들어 있다.
- **텐서 병렬 서빙** `Tensor Parallel Serving` — 한 모델을 여러 가속기에 나눠 올리는 것. 한 장에 안 들어갈 때 쓰고 장 사이 통신이 붙는다.
- **모델 샤딩** `Model Sharding` — 모델을 조각내 여러 기계에 나누는 것. 50장에서 다시 나온다.
- **자동 확장 (추론)** `Autoscaling` — 부하에 따라 서버 수를 조절하는 것. 모델 적재 시간 때문에 반응이 느려 미리 띄워 두는 여유가 필요하다.
- **예열** `Warm-up` — 처음 몇 번의 요청이 느린 것을 미리 돌려 없애는 일. 최적화된 커널이 준비되는 데 시간이 걸려서다.
- **온프레미스 서빙** `On-Premises Serving` — 자체 장비에서 돌리는 것. 데이터가 안 나가고 운영 부담이 는다.
- **하이브리드 서빙** `Hybrid Serving` — 민감한 요청은 안에서, 나머지는 밖에서 처리하는 구성. 라우팅 규칙으로 나눈다.

## 자주 헷갈리는 짝

- **배칭 (서빙)과 배치 (학습)** 같은 낱말이고 대상이 다르다.
요청을 묶는가 데이터를 묶는가.
- **처리량과 지연** 같은 점은 둘 다 속도를 나타낸다는 것.
다른 점은 방향이다. 배칭은 처리량을 올리고 지연을 늘린다.
- **KV 캐시와 접두 캐시** 같은 점은 둘 다 계산을 아낀다는 것.
다른 점은 범위다. 한 요청 안인가 요청 사이인가.
- **라우팅 (모델)과 라우팅 (전문가)** 같은 낱말이고 층이 다르다.
서버 밖에서 모델을 고르는가 모델 안에서 전문가를 고르는가.
- **게이트웨이와 로드 밸런서** 같은 점은 둘 다 앞단에 선다는 것.
다른 점은 하는 일이다. 게이트웨이는 내용을 보고 판단한다.

## 지금 움직이는 것

두 단계를 나눠 배치하는 구성이 늘고 있다. 입력을 읽는 일과 답을 만드는 일이 병목이 달라서, 같은 기계에서 섞어 돌리면 서로 방해한다는 것이 확인되었다. 그리고 30장의 답하기 전 계산이 늘면서 한 요청이 잡는 시간이 길어져 대기열 관리의 무게가 커졌다.
