# 5장 데이터베이스와 저장

<sub>1부 컴퓨터라는 바닥 · 표제어 54개 · 도해 3개</sub>

> **여는 지도** — 이 장의 낱말 쉰넷. 네 무리가 각각 다른 질문에 답한다

이 장은 데이터를 사라지지 않게 적어 두고 다시 찾는 일을 다룬다. 1장의 비트가 2장의 저장 장치에 놓이고, 그 위에 3장의 파일 시스템이 있고, 다시 그 위에 이 장의 데이터베이스가 있다.

파일에 직접 적으면 될 것 같은데 데이터베이스가 따로 있는 이유는 셋이다. 여럿이 동시에 고쳐도 안 깨지게 해야 하고, 도중에 전원이 나가도 반쯤 적힌 상태가 남으면 안 되고, 백만 줄 중에서 하나를 빨리 찾아야 한다. 이 셋이 각각 트랜잭션과 지속성과 인덱스다.

34장에서 벡터 데이터베이스가 나오는데, 그때 이 장의 낱말이 거의 그대로 쓰인다. 인덱스라는 낱말도 같고, 샤딩도 같고, 일관성 문제도 같다. 다른 것은 무엇을 기준으로 찾는가뿐이다. 값이 같은 것을 찾는 대신 뜻이 가까운 것을 찾는다.

## 한눈에 보기

| 무리 | 무엇을 다루나 | 어디서 다시 쓰나 |
|---|---|---|

| 커지면 하는 일 | 한 대로 안 될 때 나누는 방법 | 41장, 50장 |


## 표제어

### 어떻게 적을 것인가

#### 관계형 데이터베이스

<sub>Relational Database, RDB</sub>

**데이터를 행과 열로 된 표에 담고 표끼리 열쇠로 잇는 방식.**

<sub>관련어 테이블, 스키마, 정규화, SQL, 조인, NoSQL</sub>

- **테이블** `Table` — 행과 열로 된 표 하나. 행이 데이터 하나이고 열이 항목 하나다.
- **행** `Row` — 표에서 가로 한 줄. 레코드라고도 부른다.
- **열** `Column` — 표에서 세로 한 칸. 이름과 타입이 정해져 있다.
- **스키마 (DB)** `Schema` — 어떤 표에 어떤 열이 있고 각 열이 어떤 타입인지 미리 정해 둔 정의. <sub>관련어 정규화, 마이그레이션, NoSQL, 스키마(4장)</sub>
- **정규화** `Normalization` — 같은 데이터가 여러 곳에 중복되지 않게 표를 나누는 일. <sub>갈리는 자리: 데이터베이스의 정규화와 수치를 일정 범위로 맞추는 정규화가 같은 낱말이다 · 관련어 역정규화, 관계형 데이터베이스, 정규화(2부에서 다룬다)</sub>
- **역정규화** `Denormalization` — 읽기를 빠르게 하려고 일부러 중복을 두는 일. 고칠 때 여러 곳을 맞춰야 하는 부담을 진다.
- **기본 키** `Primary Key` — 한 행을 다른 행과 구별하는 열. 겹치면 안 되고 비어 있어도 안 된다.
- **외래 키** `Foreign Key` — 다른 표의 기본 키를 가리키는 열. 이 관계가 있어야 없는 것을 가리키는 데이터를 막을 수 있다.
- **조인** `Join` — 두 표를 열쇠로 이어서 함께 보는 연산. 종류에 따라 한쪽에만 있는 행을 살리기도 하고 버리기도 한다.
- **SQL** `Structured Query Language` — 관계형 데이터베이스에 무엇을 원하는지 적는 언어. <sub>관련어 질의, 실행 계획, SQL 주입(9장에서 다룬다)</sub>
- **질의** `Query` — 데이터베이스에 보내는 요청 하나. 34장의 벡터 질의, 23장 어텐션의 질의와 이름이 같고 층이 다르다.
- **NoSQL** `NoSQL` 〔유동〕 — 관계형이 아닌 데이터베이스들을 한데 묶어 부르는 이름. <sub>갈리는 자리: SQL을 안 쓴다는 뜻과 관계형이 아니라는 뜻이 섞여 있다. 요즘은 SQL을 지원하는 제품도 많다 · 관련어 문서 저장소, 키값 저장소, 일관성, 관계형 데이터베이스</sub>
- **문서 저장소** `Document Store` — JSON 같은 문서를 통째로 담는 저장소. 스키마가 느슨해 항목이 달라도 들어간다.
- **키값 저장소** `Key-Value Store` — 열쇠 하나에 값 하나를 담는 가장 단순한 저장소. 빠르고, 열쇠 말고는 못 찾는다.
- **그래프 데이터베이스** `Graph Database` — 점과 선으로 된 관계를 그대로 담는 저장소. 여러 단계를 건너 이어지는 관계를 찾을 때 유리하다.
- **시계열 데이터베이스** `Time-Series Database` — 시각과 값의 쌍을 대량으로 담는 데 맞춘 저장소. 43장의 지표 수집에 쓰인다.
- **객체 저장소** `Object Storage` — 파일을 열쇠로 넣고 꺼내는 저장소. 용량당 값이 싸고 지연이 크다. 학습 데이터와 모델 파일 보관에 널리 쓰인다.

### 안 깨지게 하는 법

#### 트랜잭션

<sub>Transaction</sub>

**여러 개의 고침을 하나로 묶어서, 전부 되거나 전부 안 되게 만드는 단위.**

<sub>관련어 ACID, 커밋, 롤백 (트랜잭션), 격리 수준, WAL, 경쟁 상태(3장)</sub>

- **ACID** `Atomicity, Consistency, Isolation, Durability` — 트랜잭션이 지켜야 할 네 가지 성질을 묶어 부르는 이름. <sub>관련어 트랜잭션, 격리 수준, 지속성, BASE</sub>
- **커밋 (트랜잭션)** `Commit` — 트랜잭션의 결과를 확정하는 일. 7장의 버전 관리 커밋과 이름이 같고 다른 것이다.
- **롤백 (트랜잭션)** `Rollback` — 트랜잭션을 취소하고 시작 전 상태로 되돌리는 일. 7장의 배포 롤백과 이름만 같다.
- **격리 수준** `Isolation Level` — 동시에 도는 트랜잭션이 서로의 중간 상태를 얼마나 볼 수 있는지 정한 단계. <sub>갈리는 자리: 같은 이름의 격리 수준이 제품마다 다르게 구현되어 있다 · 관련어 트랜잭션, 락, MVCC</sub>
- **MVCC** `Multi-Version Concurrency Control` — 같은 데이터의 여러 판을 함께 들고 있어서, 읽는 쪽이 쓰는 쪽을 안 기다리게 하는 방식. 다중 버전 동시성 제어라고 옮긴다. 오래된 버전을 치우는 일이 따로 필요해진다.
- **WAL** `Write-Ahead Log` — 고치기 전에 무엇을 고칠지 먼저 순서대로 적어 두는 기록. 이것 덕에 도중에 죽어도 복구된다. 3장의 저널링과 같은 발상이다.
- **데드락 (DB)** `Deadlock` — 두 트랜잭션이 서로가 잡은 행을 기다려 멈추는 상태. 데이터베이스가 감지해서 한쪽을 취소한다.
- **낙관적 락** `Optimistic Locking` — 먼저 고치고 저장할 때 버전이 안 바뀌었는지 확인하는 방식. 충돌이 드물 때 유리하다.
- **비관적 락** `Pessimistic Locking` — 고치기 전에 미리 잠그는 방식. 충돌이 잦을 때 유리하고 기다림이 는다.

### 빨리 찾는 법

#### 인덱스

<sub>Index</sub>

**어떤 열의 값을 정렬해 따로 적어 두고, 그 값으로 행을 빨리 찾게 만든 구조.**

<sub>관련어 B 트리, 해시 인덱스, 카디널리티, 풀 스캔, 벡터 인덱스(34장에서 다룬다)</sub>

- **B 트리** `B-Tree` — 정렬 상태를 유지하며 층이 얕게 자라는 트리. 범위 조회에 강해서 대부분의 데이터베이스 인덱스가 이 계열이다.
- **해시 인덱스** `Hash Index` — 해시값으로 자리를 바로 찾는 인덱스. 값이 같은 것을 찾을 때 가장 빠르고, 범위 조회는 못 한다.
- **복합 인덱스** `Composite Index` — 여러 열을 묶어 만든 인덱스. 열 순서가 중요해서, 앞쪽 열로 시작하는 조건에만 쓰인다.
- **카디널리티** `Cardinality` — 한 열에 서로 다른 값이 몇 가지나 되는지를 뜻하는 값의 다양함. 높을수록 인덱스가 잘 듣는다.
- **풀 스캔** `Full Scan` — 표를 처음부터 끝까지 훑는 일. 인덱스를 못 쓰거나 어차피 대부분을 읽어야 할 때 일어난다.
- **실행 계획** `Execution Plan` — 데이터베이스가 질의를 어떤 순서로 어떻게 처리할지 정한 계획. <sub>관련어 인덱스, 풀 스캔, 질의 최적화</sub>
- **질의 최적화** `Query Optimization` — 같은 결과를 더 싸게 얻는 계획을 고르는 일. 데이터베이스가 자동으로 하고, 사람이 힌트를 주기도 한다.
- **N+1 문제** `N+1 Problem` — 목록을 가져온 뒤 항목마다 다시 질의를 보내서 요청이 폭증하는 문제. 한 번에 이어서 가져오면 해결된다.

### 커지면 하는 일

#### 샤딩

<sub>Sharding</sub>

**데이터를 여러 대에 나눠 담아서 한 대의 한계를 넘는 방법.**

<sub>관련어 파티셔닝, 복제, 샤드 키, 일관성</sub>

- **파티셔닝** `Partitioning` — 한 표를 조각으로 나누는 일. 같은 기계 안에서 나누기도 하고 여러 기계에 나누기도 한다. 후자가 샤딩이다.
- **복제** `Replication` — 같은 데이터를 여러 대에 똑같이 두는 일. <sub>관련어 읽기 복제본, 일관성, 장애 조치</sub>
- **읽기 복제본** `Read Replica` — 읽기 전용으로 쓰는 복제본. 읽기 부하를 나누고, 조금 낡은 데이터를 보게 된다.
- **장애 조치** `Failover` — 주 서버가 죽었을 때 복제본을 주 서버로 승격하는 일. 자동으로 하면 빠르고, 둘 다 자기가 주인이라고 믿는 사고가 날 수 있다.
- **일관성** `Consistency` 〔유동〕 — 어느 서버에 물어봐도 같은 답이 나오는 성질. <sub>갈리는 자리: ACID의 일관성과 분산 시스템의 일관성이 다른 뜻인데 같은 낱말이다 · 관련어 결과적 일관성, CAP 정리, 복제</sub>
- **결과적 일관성** `Eventual Consistency` — 시간이 지나면 결국 같아진다는 보장. 그동안은 서버마다 다른 값이 보인다.
- **CAP 정리** `CAP Theorem` 〔유동〕 — 분산 저장소가 일관성과 가용성과 분단 내성 셋을 동시에 다 가질 수 없다는 정리. 널리 인용되지만 원래 조건보다 넓게 쓰여서 오해가 많다.
- **백업** `Backup` — 다른 곳에 따로 떠 두는 사본. 복제와 달리 실수로 지운 것도 되살릴 수 있다.
- **복구 시점 목표** `Recovery Point Objective, RPO` — 사고가 났을 때 잃어도 되는 데이터의 시간 범위. 이 값이 백업 주기를 정한다.

### 분석용 저장

**운영용 저장과 분석용 저장의 갈림**

| 자리 | 무엇을 담고 어떻게 쓰나 | 성격 |

|---|---|---|

| 운영 데이터베이스 | 지금 서비스가 읽고 쓰는 데이터 | 짧은 질의, 많은 쓰기 |

| 데이터 웨어하우스 | 분석하려고 모아 정리한 데이터 | 긴 질의, 대량 읽기 |

| 데이터 레이크 | 정리하지 않고 원본 그대로 쌓아 둔 것 | 나중에 정할 수 있다 |

| 레이크하우스 | 레이크 위에 표 구조를 얹은 것 | 둘을 합치려는 시도 |

| 피처 스토어 | 학습과 서빙에 같이 쓰는 특징 값 | 12장에서 다시 나온다 |

가르는 기준은 질의의 모양이다. 한 행을 자주 읽는가,
아니면 한 열을 통째로 읽는가. 뒤쪽이면 열 단위로 저장하는 편이 훨씬 빠르다.

- **데이터 웨어하우스** `Data Warehouse` — 분석하려고 여러 곳의 데이터를 모아 정리해 둔 저장소. 대개 열 단위로 저장한다.
- **데이터 레이크** `Data Lake` 〔유동〕 — 정리하지 않은 원본을 그대로 쌓아 두는 저장소. 정리를 미룰 수 있어 편하고, 관리를 안 하면 무엇이 있는지 모르게 된다.
- **ETL** `Extract, Transform, Load` — 데이터를 꺼내고 모양을 바꿔 넣는 절차. 순서를 바꿔 먼저 넣고 나중에 바꾸는 방식도 널리 쓰인다.
- **열 지향 저장** `Columnar Storage` — 한 열의 값들을 이어서 저장하는 방식. 같은 종류가 모여 있어 압축이 잘 되고, 한 열만 읽는 질의가 빠르다.
- **OLTP** `Online Transaction Processing` — 짧은 트랜잭션을 많이 처리하는 성격의 일. 운영 데이터베이스가 여기 속한다.
- **OLAP** `Online Analytical Processing` — 대량을 훑어 집계하는 성격의 일. 웨어하우스가 여기 속한다.
- **캐시 계층** `Cache Layer` — 데이터베이스 앞에 두고 자주 읽는 것을 담아 두는 저장소. 원본이 바뀌었을 때 언제 버릴지가 늘 문제다.

## 자주 헷갈리는 짝

- **복제와 백업** 같은 점은 둘 다 사본을 만든다는 것.
다른 점은 실수를 따라가는가다. 복제는 지운 것도 같이 지우고 백업은 안 지운다.
- **샤딩과 파티셔닝** 같은 점은 둘 다 데이터를 조각으로 나눈다는 것.
다른 점은 여러 기계에 나누는가다. 한 기계 안이면 파티셔닝이다.
- **일관성 (ACID)과 일관성 (분산)** 같은 글자이고 뜻이 다르다.
앞은 규칙을 안 깬다는 뜻이고 뒤는 어디서 읽어도 같다는 뜻이다.
- **인덱스와 캐시** 같은 점은 둘 다 조회를 빠르게 한다는 것.
다른 점은 인덱스가 찾는 길을 만들고 캐시가 결과를 들고 있다는 것.
- **스키마와 스키마** 데이터베이스의 표 정의, 4장의 데이터 형식 정의,
36장의 도구 정의가 전부 같은 낱말이다. 셋 다 미리 정해 둔 모양이라는 공통점은 있다.

## 지금 움직이는 것

저장소 선택이 다시 갈리고 있다. 오래 관계형이 기본값이었다가 한동안 관계형이 아닌 쪽으로 넓게 퍼졌고, 지금은 관계형 제품이 문서와 벡터를 같이 담는 쪽으로 돌아왔다. 34장에서 전용 벡터 저장소와 기존 데이터베이스의 확장 기능 중 무엇을 고를지가 같은 이야기의 연장으로 나온다.

## 더 볼 곳

여기서 나온 인덱스와 샤딩이 34장에서 벡터 이야기로 돌아온다. 트랜잭션과 격리는 8장의 분산 이야기로 이어지고, 데이터 파이프라인은 12장에서 학습 데이터 이야기가 된다.
