# 39장 코딩 에이전트

<sub>7부 에이전트 · 표제어 76개 · 도해 4개</sub>

> **여는 지도** — 이 장의 낱말 일흔여섯. 코드를 고치는 에이전트가 도는 일곱 자리

이 장은 코드를 고치는 일에 에이전트를 붙인 경우를 다룬다. 7부에서 가장 널리 쓰이는 자리이고, 가장 잘 도는 자리이기도 하다.

잘 도는 이유가 분명하다. 확인이 기계로 된다. 컴파일이 되는지, 테스트가 통과하는지, 타입이 맞는지를 사람 없이 판정할 수 있다. 30장에서 말한 검증 가능한 보상이 여기 있다. 그래서 고치고 돌려 보고 다시 고치는 고리가 성립한다.

7장의 낱말이 통째로 돌아온다. 브랜치, 커밋, 테스트, 풀 리퀘스트. 달라진 것은 그 절차의 어느 칸을 사람이 하고 어느 칸을 기계가 하는가다. 적는 시간이 줄고 검토하는 시간이 늘었다는 것이 지금 일어난 변화이고, 그래서 리뷰와 테스트의 값이 올라갔다.

## 표제어

### 저장소를 이해하기

#### 코딩 에이전트 〔신조〕

<sub>Coding Agent</sub>

**코드를 읽고 고치고 확인하는 일을 여러 걸음에 걸쳐 스스로 진행하는 시스템.**

갈리는 자리 — 자동완성 수준부터 자율 실행까지 같은 낱말로 부른다

생긴 때 — 2023년 이후 낱말이 자리 잡았다

<sub>관련어 편집 도구, 검증 고리, 코드베이스 탐색, 에이전트(35장)</sub>

- **코드베이스 탐색** `Codebase Navigation` — 저장소에서 지금 고칠 것이 어디 있는지 찾아가는 일. <sub>관련어 심볼 검색, 코드 검색(34장), 언어 서버(7장), 의존 파악</sub>
- **심볼 검색** `Symbol Search` — 함수나 클래스 이름으로 정의와 사용처를 찾는 일. 문자열 검색보다 정확하다.
- **참조 찾기** `Find References` — 어느 것이 어디서 쓰이는지 찾는 일. 고치기 전에 영향 범위를 아는 데 필요하다.
- **의존 파악** `Dependency Analysis` — 무엇이 무엇에 기대는지 파악하는 일. 고치면 무엇이 깨지는지의 근거가 된다.
- **저장소 지도** `Repository Map` 〔신조〕 — 저장소의 구조와 주요 파일을 요약해 문맥에 넣는 것. 전부 읽지 않고도 대략을 알게 한다. <sub>생긴 때: 2023년 이후 쓰인다</sub>
- **규약 파악** `Convention Learning` 〔신조〕 — 그 저장소의 코드 스타일과 관례를 파악해 따르는 일. 안 하면 겉도는 코드가 들어온다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **프로젝트 지침 파일** `Project Instructions` 〔신조〕 — 저장소에 두는 에이전트용 안내 문서. 빌드 방법과 규약과 하지 말아야 할 것을 적어 둔다. 실제로 품질을 크게 올린다. <sub>생긴 때: 2024년 이후 널리 쓰인다</sub>
- **컨텍스트 파일** `Context File` 〔신조〕 — 에이전트가 매번 읽는 규칙 파일. 지침 파일과 같은 것을 다르게 부르는 이름이다. <sub>생긴 때: 2024년 이후 쓰인다</sub>

### 코드를 고치는 방식

**편집 방식 네 가지**

| 방식 | 어떻게 하나 | 장점 | 단점 |

|---|---|---|---|

| 전체 재작성 | 파일을 통째로 다시 쓴다 | 형식이 안 깨진다 | 토큰이 많이 든다 |

| 검색 치환 | 옛 문자열을 새것으로 | 토큰이 적다 | 안 맞으면 실패 |

| 줄 번호 편집 | 몇 번째 줄을 고친다 | 정확하다 | 줄이 밀리면 어긋난다 |

| 패치 형식 | 차이만 적어 적용한다 | 표준이고 검토가 쉽다 | 형식이 까다롭다 |

검색 치환이 널리 쓰인다. 고칠 부분의 앞뒤를 충분히 포함해
한 군데에만 맞게 하는 것이 요령이다.
안 맞으면 실패를 알려 주고 다시 시도하게 하는 편이,
비슷한 곳에 잘못 적용하는 것보다 낫다.

- **편집 도구** `Edit Tool` — 파일을 고치는 도구. 어떤 방식으로 고치게 하느냐가 성공률을 크게 가른다.
- **검색 치환 편집** `Search-Replace Edit` 〔신조〕 — 옛 문자열과 새 문자열을 주어 바꾸는 방식. 정확히 한 군데에만 맞아야 안전하다. <sub>생긴 때: 2023년 이후 널리 쓰인다</sub>
- **패치 (코드)** `Patch` — 변경 내용을 차이 형식으로 적은 것. 7장의 디프와 같은 형식이다.
- **전체 재작성** `Full Rewrite` — 파일을 통째로 다시 쓰는 방식. 확실하고 비싸며 안 건드릴 부분까지 바뀔 위험이 있다.
- **최소 변경** `Minimal Diff` — 필요한 만큼만 고치는 원칙. 검토가 쉬워지고 사고가 준다. 지시로 명시하지 않으면 잘 안 지켜진다.
- **형식 유지** `Formatting Preservation` — 원래 들여쓰기와 스타일을 그대로 두는 것. 포매터를 돌려 맞추는 편이 확실하다.
- **다중 파일 편집** `Multi-File Edit` — 여러 파일을 함께 고치는 일. 하나만 고치고 나머지를 빠뜨리면 깨진다.
- **원자적 변경** `Atomic Change` — 한 묶음의 변경이 전부 되거나 전부 안 되게 하는 것. 5장의 트랜잭션과 같은 발상이다.
- **코드 생성** `Code Generation` — 코드를 새로 만들어 내는 일. 고치는 것보다 쉽고, 기존 코드와 어울리게 만드는 것이 어렵다.
- **스캐폴딩** `Scaffolding` — 정해진 틀의 코드를 자동으로 만들어 두는 것. 반복되는 구조에 잘 맞는다.

### 확인하고 다시 고치기

#### 검증 고리

<sub>Verification Loop</sub>

**고치고, 돌려 보고, 실패하면 오류를 읽고 다시 고치기를 반복하는 구조.**

<sub>관련어 테스트 실행, 실패 읽기, 반성(37장), 종료 조건(35장)</sub>

- **테스트 실행** `Test Execution` — 시험을 돌려 통과 여부를 확인하는 일. 성공 조건을 기계로 판정하는 가장 흔한 수단이다.
- **빌드 확인** `Build Check` — 컴파일이나 빌드가 되는지 확인하는 일. 가장 싸고 빠른 검증이다.
- **타입 검사** `Type Check` — 타입이 맞는지 확인하는 일. 돌려 보지 않고 잡히는 오류가 많아 고리를 빠르게 만든다.
- **린트** `Lint` — 스타일과 흔한 실수를 검사하는 일. 7장에서 정의했고 여기서는 자동 확인의 한 단계다.
- **실패 읽기** `Failure Interpretation` — 오류 메시지와 스택 트레이스를 읽어 원인을 짚는 일. 이 능력이 이 분야 성능의 큰 부분이다.
- **시험 먼저 쓰기** `Test-First with Agents` 〔신조〕 — 고치기 전에 실패하는 시험을 먼저 만들게 하는 방식. 무엇을 고칠지 명확해지고 다 고쳤는지 판정된다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **회귀 확인** `Regression Check` — 고치면서 다른 것이 깨지지 않았는지 확인하는 일. 시험이 없으면 확인할 방법이 없다.
- **시험 조작** `Test Gaming` 〔신조〕 — 코드를 고치는 대신 시험을 고쳐 통과시키는 것. 26장의 보상 해킹이 여기서 나타난 형태다. 시험 파일 변경을 막거나 따로 확인해야 한다. <sub>생긴 때: 2024년 이후 관찰된다</sub>
- **반복 상한** `Iteration Limit` — 몇 번까지 고쳐 볼지의 상한. 진전 없이 도는 것을 막는다.

### 사람에게 넘기기

- **변경 요약** `Change Summary` — 무엇을 왜 어떻게 고쳤는지 정리해 사람에게 넘기는 글. <sub>관련어 풀 리퀘스트(7장), 커밋 메시지(7장), 코드 리뷰(7장)</sub>
- **풀 리퀘스트 생성** `PR Creation` — 고친 것을 브랜치에 담아 검토 요청을 여는 일. 7장의 절차를 그대로 쓴다.
- **리뷰 대상 크기** `Review Size` — 한 번에 검토할 변경의 양. 커지면 검토가 부실해진다. 에이전트가 만든 변경은 커지기 쉬워 특히 문제가 된다.
- **코드 리뷰 에이전트** `Code Review Agent` 〔신조〕 — 사람 대신 또는 사람보다 먼저 코드를 검토하는 에이전트. 규칙 위반과 흔한 실수를 잡고, 설계 판단은 사람 몫으로 남는다. <sub>생긴 때: 2023년 이후 쓰인다</sub>
- **자동 수정 제안** `Suggested Fix` — 검토에서 지적한 것을 고친 코드로 같이 제안하는 것. 받아들이기가 쉬워진다.
- **승인 정책** `Merge Policy` — 에이전트가 만든 변경을 어떤 조건에서 합칠지 정한 규칙. 사람 승인을 반드시 요구할지가 핵심이다.
- **책임 귀속** `Accountability` — 에이전트가 만든 코드에 문제가 생겼을 때 누가 책임지는가. 지금은 합친 사람이 진다는 것이 일반적인 정리다.

### 무엇을 막아야 하나

**코딩 에이전트에서 막아야 할 여섯 가지**

| 위험 | 무슨 일이 생기나 | 막는 방법 |

|---|---|---|

| 운영 접근 | 실제 데이터를 건드린다 | 격리된 환경만 제공 |

| 비밀 유출 | 열쇠가 로그나 코드에 남는다 | 환경 변수와 검사 |

| 의존성 추가 | 모르는 꾸러미를 설치한다 | 승인과 허용 목록 |

| 넓은 삭제 | 필요한 파일을 지운다 | 버전 관리와 읽기 전용 |

| 시험 조작 | 시험을 고쳐 통과시킨다 | 시험 파일 보호 |

| 외부 발신 | 코드나 데이터를 밖으로 보낸다 | 네트워크 차단 |

버전 관리가 가장 강한 안전망이다.
모든 변경이 기록에 남고 되돌릴 수 있으면 대부분의 실수가 복구된다.
그래서 에이전트에게 일을 시키기 전에 커밋해 두는 것이 기본 습관이 되었다.

- **격리된 개발 환경** `Isolated Dev Environment` — 운영과 분리된 작업 공간. 8장의 컨테이너나 별도 기계를 쓴다.
- **비밀 검사** `Secret Scanning` — 코드에 열쇠나 비밀번호가 들어갔는지 검사하는 일. 커밋 전에 자동으로 돌린다.
- **의존성 승인** `Dependency Approval` — 새 꾸러미를 추가할 때 사람이 확인하는 절차. 47장의 공급망 위험을 막는다.
- **명령 허용 목록** `Command Allowlist` — 실행할 수 있는 명령을 나열해 제한하는 것. 막을 것을 나열하는 방식보다 안전하다.
- **작업 전 커밋** `Commit Before Work` — 에이전트를 돌리기 전에 현재 상태를 기록해 두는 습관. 되돌릴 근거가 된다.
- **브랜치 격리** `Branch Isolation` — 에이전트가 별도 브랜치에서만 일하게 하는 것. 본줄기가 안 깨진다.
- **워크트리 분리** `Worktree Separation` — 여러 에이전트가 각자 다른 작업 디렉터리에서 일하게 하는 것. 38장의 자원 충돌을 없앤다.

### 무엇이 잘 안 되나

- **큰 저장소 문제** `Large Codebase Problem` 〔신조〕 — 저장소가 크면 무엇이 어디 있는지 못 찾아 헤매는 것. 지침 파일과 탐색 도구로 완화한다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **설계 판단** `Design Decision` — 어떤 구조로 만들지 정하는 일. 정답이 여럿이고 맥락에 달려 있어 자동화가 어렵다.
- **암묵 지식** `Tacit Knowledge` — 문서에 없고 사람들만 아는 사정. 왜 이 코드가 이상하게 생겼는지 같은 것. 지침 파일에 적어 두면 일부는 해결된다.
- **과잉 수정** `Over-editing` 〔신조〕 — 시킨 것 외에 다른 부분까지 고치는 것. 검토 부담이 커지고 사고 위험이 는다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **그럴듯한 오답** `Plausible Wrong Code` — 돌아가는 것처럼 보이는데 틀린 코드. 시험이 없으면 통과한다.
- **환각 API** `Hallucinated API` — 없는 함수나 옵션을 있는 것처럼 쓰는 것. 타입 검사나 실행으로 대부분 잡힌다.
- **옛 방식 사용** `Outdated Pattern` — 학습 시점의 낡은 관행을 쓰는 것. 지원 중단된 함수를 쓰는 경우가 흔하다.
- **성능 무관심** `Performance Blindness` — 돌아가긴 하는데 비효율적인 코드를 만드는 것. 6장의 빅오 표기를 기준으로 검토해야 잡힌다.
- **보안 취약 코드** `Insecure Code` — 9장의 흔한 취약점을 그대로 만들어 내는 것. 정적 분석을 고리에 넣어야 한다.

### 어디에 붙이나

- **자동완성** `Code Completion` — 입력 중에 이어질 코드를 제안하는 기능. 지연이 짧아야 해서 작은 모델을 쓴다.
- **인라인 편집** `Inline Edit` — 선택한 부분을 지시대로 고치는 기능. 범위가 좁아 확인이 쉽다.
- **터미널 에이전트** `Terminal Agent` 〔신조〕 — 명령줄에서 도는 코딩 에이전트. 파일과 명령 실행 도구를 갖고 여러 걸음을 돈다. <sub>생긴 때: 2024년 이후 널리 쓰인다</sub>
- **이슈 기반 에이전트** `Issue-Driven Agent` 〔신조〕 — 이슈를 받아 스스로 고치고 풀 리퀘스트를 여는 구성. 사람이 확인하는 자리가 마지막에만 있다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **마이그레이션** `Migration` — 옛 방식을 새 방식으로 일괄 변환하는 작업. 패턴이 정해져 있어 에이전트에 잘 맞는다.
- **테스트 작성** `Test Generation` — 기존 코드에 시험을 만들어 붙이는 일. 없던 시험을 채우는 데 유용하고, 지금 동작을 그대로 굳히는 위험이 있다.
- **문서화 생성** `Doc Generation` — 코드에서 문서를 만들어 내는 일. 코드와 어긋나지 않게 유지하는 것이 과제다.
- **버그 재현** `Bug Reproduction` — 보고된 문제를 재현하는 시험을 먼저 만드는 일. 고쳤는지 판정하는 기준이 된다.
- **성능 개선** `Performance Optimization` — 느린 부분을 찾아 고치는 일. 측정이 있어야 성립한다. 7장의 프로파일러를 도구로 붙인다.

### 평가하기

- **코딩 벤치마크** `Coding Benchmark` — 코딩 능력을 재는 시험 묶음. 함수 하나를 적게 하는 HumanEval과 MBPP가 오래 쓰였고, 지금은 실제 저장소의 이슈를 고치게 하는 SWE-bench 쪽이 에이전트 평가의 기준이 되었다. 42장에 시험 이름들을 모아 두었다.
- **SWE-bench** `SWE-bench` 〔신조〕 — 실제 저장소에 올라왔던 이슈를 주고 코드를 고쳐 원래 있던 시험을 통과시키게 하는 평가. 여러 파일을 오가야 하고 채점이 시험 통과 여부라 기계로 확실히 판정된다. 사람이 문제를 검수해 걸러 낸 부분집합이 따로 쓰이고, 공개 저장소를 쓰기 때문에 오염 논란이 늘 따라붙는다. <sub>생긴 때: 2023년 무렵 나왔고 2024년 이후 에이전트 평가의 기준으로 자리 잡았다</sub>
- **통과율** `Pass Rate` — 주어진 문제 중 시험을 통과한 비율. 여러 번 시도해서 하나만 맞아도 되는지 한 번에 맞아야 하는지를 구별해 적어야 한다.
- **벤치마크 오염 (코드)** `Benchmark Contamination` — 시험 문제가 학습 데이터에 들어간 상태. 공개 저장소를 쓰므로 특히 심하다. 42장에서 다시 다룬다.
- **실사용 지표** `Real-World Metric` — 합쳐진 변경의 비율, 되돌린 비율, 검토에 든 시간 같은 값. 벤치마크 점수보다 이쪽이 실제를 말한다.
- **수용률** `Acceptance Rate` — 제안된 코드가 실제로 받아들여진 비율. 도구의 실효를 재는 기본 값이다.

### 무엇을 만들지 먼저 적기

#### 스펙 주도 개발 〔신조〕

<sub>Spec-Driven Development, SDD</sub>

**코드가 아니라 명세를 원본으로 두고, 명세에서 계획과 코드와 시험을 만들어 내는 방식.**

갈리는 자리 — 문서를 먼저 쓰는 관행 전반을 가리키기도 하고 정해진 세 단계 절차를 가리키기도 한다

생긴 때 — 2024년 이후 이름이 자리 잡았다

<sub>관련어 스펙 파일, 수용 기준, 스펙 드리프트, 계획 문서(37장)</sub>

- **스펙 파일** `Spec File` 〔신조〕 — 무엇을 만들지 적어 저장소에 두는 문서. 코드와 같이 버전 관리되고 같이 검토된다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **수용 기준** `Acceptance Criteria` — 무엇이 되면 이 일이 끝난 것인지 적은 조건. 기계로 확인할 수 있게 적으면 그대로 시험이 된다.
- **단계 문서** `Staged Documents` 〔신조〕 — 요구와 설계와 작업을 나눠 적은 문서 묶음. 단계마다 사람이 확인하고 넘어가게 만든다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **스펙 드리프트** `Spec Drift` 〔신조〕 — 명세와 실제 코드가 시간이 지나며 갈라지는 것. <sub>생긴 때: 2024년 이후 쓰인다 · 관련어 스펙 주도 개발, 스펙 파일, 문서화(7장)</sub>
- **역명세** `Reverse Specification` 〔신조〕 — 이미 있는 코드에서 명세를 뽑아내는 일. 옛 시스템을 옮기기 전에 무엇을 하는지 정리하는 데 쓴다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **바이브 코딩** `Vibe Coding` 〔신조〕 — 코드를 자세히 읽지 않고 되는지만 보며 만들어 가는 방식. 시제품과 개인 작업에는 빠르고, 운영에 들어가는 코드에는 위험하다는 지적이 따라온다. <sub>생긴 때: 2025년 무렵 이름이 붙었다</sub>
- **명세 검증** `Spec Validation` 〔신조〕 — 만들어진 것이 명세를 만족하는지 확인하는 단계. 수용 기준을 시험으로 바꿔 두면 자동으로 된다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **작업 쪼개기 파일** `Task File` 〔신조〕 — 명세에서 뽑아낸 작업 목록을 적어 둔 파일. 37장의 작업 목록을 저장소에 두는 형태다. <sub>생긴 때: 2024년 이후 쓰인다</sub>

## 자주 헷갈리는 짝

- **자동완성과 코딩 에이전트** 같은 점은 둘 다 코드를 만들어 준다는 것.
다른 점은 걸음 수와 확인 여부다. 앞은 제안하고 끝이다.
- **검증 고리와 반성** 같은 점은 둘 다 다시 시도한다는 것.
다른 점은 신호의 출처다. 검증 고리는 기계가 판정한다.
- **패치와 전체 재작성** 같은 점은 둘 다 파일을 고친다는 것.
다른 점은 범위와 비용이다. 검토 부담도 크게 다르다.
- **시험 작성과 시험 조작** 같은 점은 둘 다 시험을 건드린다는 것.
다른 점은 목적이다. 뒤쪽은 통과시키려고 고치는 것이라 막아야 한다.
- **브랜치 격리와 워크트리 분리** 같은 점은 둘 다 충돌을 막는다는 것.
다른 점은 층이다. 앞은 기록이고 뒤는 디렉터리다.
- **스펙 주도 개발과 테스트 주도 개발** 같은 점은 둘 다 만들기 전에 무엇이 맞는지 정한다는 것.
다른 점은 형식이다. 앞은 글이고 뒤는 실행되는 시험이다. 수용 기준을 시험으로 적으면 둘이 만난다.
- **바이브 코딩과 스펙 주도 개발** 같은 점은 둘 다 코드를 직접 안 적는다는 것.
다른 점은 무엇을 확인하는가다. 앞은 결과만 보고 뒤는 명세를 본다.
- **명세 (0장)와 스펙 파일** 같은 낱말에서 왔다.
다른 점은 대상이다. 앞은 프로토콜 규격이고 뒤는 이번에 만들 것을 적은 문서다.

## 지금 움직이는 것

무게중심이 적는 것에서 검토하는 것으로 옮겨 갔다. 코드를 만들어 내는 속도가 빨라지면서 병목이 리뷰로 이동했고, 그래서 변경을 작게 유지하고 시험을 갖추는 규율의 값이 올라갔다. 동시에 여러 작업을 병렬로 돌리는 구성이 늘면서 작업 공간을 어떻게 나눌 것인가가 실무 문제가 되었다.
