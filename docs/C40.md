# 40장 컴퓨터를 쓰는 에이전트

<sub>7부 에이전트 · 표제어 63개 · 도해 4개</sub>

> **여는 지도** — 이 장의 낱말 예순셋. 화면을 보고 조작하기까지 다섯 자리

이 장은 사람이 쓰는 화면을 그대로 다루는 에이전트를 다룬다. 39장이 코드를 고쳤다면 여기서는 마우스와 키보드를 쓴다.

왜 이렇게 하는가. API가 없는 시스템이 많아서다. 사내 시스템, 오래된 업무 프로그램, 남의 웹서비스. 사람은 화면으로 쓸 수 있는데 프로그램이 쓸 통로가 없다. 그 자리를 메우는 것이 이 방식이다.

대가가 크다. 느리고, 잘 깨지고, 위험하다. 화면이 조금만 바뀌어도 못 찾고, 클릭 하나가 되돌릴 수 없는 결과를 만든다. 그래서 이 장은 다른 어느 장보다 안전 장치 이야기가 많다. API가 있으면 API를 쓰는 것이 언제나 낫다는 것이 첫째 원칙이다.

## 표제어

### 화면을 읽는 방법

#### 컴퓨터 사용 〔신조〕

<sub>Computer Use</sub>

**화면을 보고 마우스와 키보드를 조작해 사람처럼 프로그램을 쓰는 방식.**

생긴 때 — 2024년 이후 낱말이 자리 잡았다

<sub>관련어 화면 이해(29장), 좌표 지목, 접근성 트리, 브라우저 자동화</sub>

**화면을 읽는 세 가지 방법**

| 방법 | 무엇을 주나 | 장점 | 단점 |

|---|---|---|---|

| 화면 캡처 | 이미지 그대로 | 어디서나 된다 | 토큰이 많고 좌표가 부정확 |

| 접근성 트리 | 요소의 구조와 이름 | 정확하고 가볍다 | 지원 안 하는 앱이 있다 |

| DOM | 웹페이지의 문서 구조 | 정확하고 조작이 쉽다 | 웹에서만 된다 |

웹이면 DOM을 쓰는 것이 훨씬 낫다.
버튼을 좌표로 찍는 대신 어느 요소인지 지목할 수 있어서
화면이 조금 바뀌어도 안 깨진다.
이미지만 쓰는 방식은 다른 길이 없을 때의 선택이다.

- **화면 캡처** `Screenshot` — 지금 화면을 이미지로 찍은 것. 모델에게 주는 가장 단순한 입력이고 토큰을 많이 먹는다.
- **접근성 트리** `Accessibility Tree` — 화면 요소의 이름과 역할과 상태를 담은 구조. 원래 보조 기술을 위해 만들어진 것이고 에이전트에도 쓰인다.
- **DOM** `Document Object Model` — 웹페이지의 문서 구조. 요소를 정확히 지목하고 조작할 수 있게 한다.
- **요소 인식** `Element Detection` — 화면에서 버튼과 입력창 같은 것을 찾아내는 일. 이미지만 보고 하면 틀리는 경우가 많다.
- **요소 지목** `Element Selection` — 조작할 대상을 가리키는 방식. 좌표로 찍는 것보다 요소 식별자로 가리키는 편이 안정적이다.
- **좌표 지목** `Coordinate Grounding` 〔신조〕 — 화면의 몇 번째 점을 클릭할지 정하는 일. 지금 이 분야에서 가장 자주 틀리는 자리다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **요소 표시** `Set-of-Marks` 〔신조〕 — 화면 요소에 번호를 붙여 표시해 두고 번호로 지목하게 하는 기법. 좌표 오류를 크게 줄인다. <sub>생긴 때: 2023년 이후 쓰인다</sub>
- **화면 요약** `Screen Summary` — 화면 내용을 글로 정리해 문맥에 넣는 것. 이미지보다 토큰을 아낀다.
- **시각 정보와 구조 정보** `Vision plus Structure` — 이미지와 접근성 정보를 같이 주는 방식. 이미지로 상황을 보고 구조로 정확히 지목한다.

### 어떻게 조작하나

- **조작 도구** `Action Tools` — 마우스와 키보드 동작을 수행하는 도구 묶음. <sub>관련어 클릭, 입력, 대기, 승인(35장)</sub>
- **클릭** `Click` — 마우스로 누르는 동작. 대상이 무엇인지 확인하고 눌러야 안전하다.
- **텍스트 입력** `Type` — 키보드로 글자를 넣는 동작. 입력창에 초점이 가 있는지 먼저 확인해야 한다.
- **키 조합** `Key Combination` — 여러 키를 함께 누르는 동작. 복사와 붙여넣기와 저장 같은 것.
- **스크롤** `Scroll` — 화면을 위아래로 옮기는 동작. 안 보이는 부분을 보려면 필요하고, 얼마나 옮길지 판단이 어렵다.
- **끌어놓기** `Drag and Drop` — 눌러서 옮기는 동작. 좌표 정밀도가 특히 필요해 성공률이 낮다.
- **대기** `Wait` — 화면이 바뀔 때까지 기다리는 동작. 없으면 아직 안 뜬 화면을 보고 판단한다.
- **조건부 대기** `Wait for Condition` — 정해진 요소가 나타날 때까지 기다리는 방식. 정해진 시간을 기다리는 것보다 안정적이다.
- **초점** `Focus` — 지금 입력을 받는 요소. 초점이 어디 있는지 모르면 엉뚱한 곳에 입력한다.
- **화면 탐색** `Navigation` — 다른 화면이나 페이지로 이동하는 것. 4장의 주소를 직접 여는 편이 클릭으로 찾아가는 것보다 빠르고 안정적이다.

### 왜 잘 깨지나

#### 취약성

<sub>Brittleness</sub>

**화면이 조금만 달라져도 동작이 실패하는 성질.**

<sub>관련어 요소 지목, 조건부 대기, 상태 확인, 복구</sub>

- **화면 변화 감지** `Change Detection` — 조작 뒤에 화면이 실제로 바뀌었는지 확인하는 것. 안 바뀌었으면 클릭이 안 먹은 것이다.
- **상태 확인** `State Verification` — 지금 어느 화면에 있는지 매 걸음 확인하는 것. 착각한 채로 진행하면 엉뚱한 곳에서 조작한다.
- **예상 못 한 창** `Unexpected Dialog` — 알림이나 동의 창이 갑자기 뜨는 상황. 흐름이 끊기고, 잘못 누르면 되돌릴 수 없다.
- **로딩 대기** `Loading Handling` — 아직 안 뜬 화면을 기다리는 처리. 이것이 없어서 나는 실패가 가장 흔하다.
- **복구** `Recovery` — 실패한 자리에서 되돌아가 다시 시도하는 것. 처음부터 다시 하면 앞의 조작이 중복 적용된다.
- **멱등하지 않은 조작** `Non-Idempotent Action` — 두 번 하면 두 번 일어나는 조작. 4장의 멱등성이 없어서 재시도가 위험하다.
- **느린 속도** `Latency Problem` — 한 걸음마다 화면을 보고 판단하느라 느린 것. 스무 걸음이면 분 단위가 된다.
- **토큰 비용 (화면)** `Screenshot Cost` — 화면 이미지가 매 걸음 문맥에 들어가 비용이 크게 드는 것. 요약이나 구조 정보로 대체하면 준다.

### 브라우저를 다루는 경우

- **브라우저 자동화** `Browser Automation` — 웹브라우저를 프로그램으로 조작하는 것. <sub>관련어 DOM, 헤드리스, 세션 격리, 컴퓨터 사용</sub>
- **헤드리스** `Headless` — 화면을 실제로 그리지 않고 브라우저를 돌리는 방식. 빠르고 자원을 덜 쓴다.
- **셀렉터** `Selector` — 웹페이지에서 요소를 지목하는 표현. 구조가 바뀌면 안 맞아서 안정적인 것을 고르는 요령이 있다.
- **브라우저 세션** `Browser Session` — 로그인 상태와 쿠키를 담은 브라우저 쪽 상태. 4장의 쿠키가 여기 담기고, 9장의 서버 세션과 짝을 이룬다.
- **세션 격리** `Session Isolation` — 에이전트가 쓰는 브라우저를 사람 것과 분리하는 것. 안 하면 사람의 로그인 상태로 아무거나 할 수 있게 된다.
- **사람 확인 절차** `CAPTCHA` — 자동 접근을 막으려고 두는 확인 단계. 이것을 우회하는 것은 대개 이용 약관 위반이다.
- **로봇 배제 표준** `robots.txt` — 사이트가 자동 접근 범위를 적어 둔 파일. 강제력은 없고 지키는 것이 관행이다.
- **이용 약관** `Terms of Service` — 그 서비스를 어떻게 써도 되는지 정한 계약. 자동화 금지 조항이 있는 경우가 많다.
- **다운로드 처리** `File Download` — 브라우저가 받은 파일을 다루는 일. 받은 파일이 신뢰할 수 없는 입력이라는 점을 잊기 쉽다.

### 무엇을 막아야 하나

#### 조작 위험 〔신조〕

<sub>Action Risk</sub>

**화면 조작이 되돌릴 수 없는 결과를 만드는 위험.**

생긴 때 — 2024년 이후 문제로 다뤄진다

<sub>관련어 승인 지점, 금지 동작, 계정 권한, 간접 주입(47장에서 다룬다)</sub>

- **승인 지점** `Approval Checkpoint` — 되돌릴 수 없는 조작 앞에서 사람 확인을 받는 자리. 무엇에 붙일지 목록으로 정해 둔다.
- **금지 동작** `Blocked Action` — 아예 못 하게 막아 둔 조작. 결제와 계정 설정 변경 같은 것이다.
- **계정 권한 제한** `Restricted Account` — 에이전트에게 좁은 권한의 별도 계정을 주는 것. 9장의 최소 권한을 이 층에 적용한 것이다.
- **조작 기록** `Action Log` — 무엇을 언제 눌렀는지 남기는 기록. 화면 캡처를 같이 남기면 되짚기가 쉽다.
- **스테이징 환경** `Staging Environment` — 운영이 아닌 곳에서 먼저 돌려 보는 것. 7장의 스테이징이 여기서 쓰인다.
- **읽기 전용 흐름** `Read-Only Flow` — 조회만 하고 아무것도 안 바꾸는 작업. 위험이 크게 준다.
- **되돌릴 수 없는 화면** `Point of No Return` — 누르면 끝인 자리. 발송, 결제, 삭제 확인 화면이다. 미리 목록으로 정해 두고 멈춘다.
- **데이터 유출 경로** `Exfiltration Path` 〔신조〕 — 화면에서 읽은 것을 바깥으로 보낼 수 있는 통로. 읽기와 발신이 둘 다 가능하면 경로가 완성된다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **자격 증명 노출** `Credential Exposure` — 로그인 정보가 화면 캡처나 기록에 남는 것. 비밀번호 입력 화면을 안 찍는 처리가 필요하다.

### 어디에 쓰나

**쓸 만한 자리와 안 맞는 자리**

| 자리 | 왜 | 주의 |

|---|---|---|

| API 없는 사내 시스템 | 다른 통로가 없다 | 권한을 좁게 |

| 반복되는 조회 작업 | 사람이 하기 아깝다 | 읽기 전용으로 |

| 여러 사이트 비교 | 통합 API가 없다 | 약관 확인 |

| 시험 자동화 | 사람처럼 써 봐야 한다 | 안정성이 관건 |

| 결제와 계약 | 안 맞는다 | 되돌릴 수 없다 |

| 대량 수집 | 안 맞는다 | 약관과 부하 문제 |

판단 기준이 둘이다. API가 있는가, 그리고 되돌릴 수 있는가.
API가 있으면 그쪽이 빠르고 안정적이고 안전하다.
되돌릴 수 없는 일에는 사람이 마지막 버튼을 누르게 남겨 둔다.

- **업무 자동화** `Workflow Automation` — 반복되는 업무 절차를 대신하게 하는 것. 규칙이 정해진 부분은 기존 자동화 도구가 더 낫다.
- **RPA** `Robotic Process Automation` — 정해진 순서로 화면을 조작하는 오래된 자동화 방식. 규칙 기반이라 화면이 바뀌면 깨진다. 모델을 붙여 그 약점을 메우려는 시도가 있다.
- **웹 조사** `Web Research` — 여러 페이지를 돌며 정보를 모으는 작업. 읽기만 해서 위험이 작고 널리 쓰인다.
- **양식 채우기** `Form Filling` — 입력 양식을 대신 채우는 일. 제출 버튼 앞에서 멈추게 하는 것이 관행이다.
- **데이터 이관** `Data Migration` — 한 시스템에서 다른 시스템으로 옮기는 작업. 대량이면 화면 조작이 아니라 내보내기 기능을 찾는 편이 낫다.
- **접근성 시험** `Accessibility Testing` — 화면이 보조 기술로 쓸 만한지 확인하는 일. 접근성 트리를 다루는 기술이 그대로 쓰인다.

### 잘하는지 재기

- **과업 성공률** `Task Success Rate` — 주어진 일을 끝까지 해낸 비율. 이 분야의 기본 지표이고 아직 낮은 편이다.
- **걸음 수** `Step Count` — 일을 끝내는 데 쓴 조작 횟수. 적을수록 빠르고 안전하다.
- **개입 횟수** `Intervention Rate` — 사람이 끼어들어야 했던 횟수. 실용성을 재는 실질적인 값이다.
- **웹 벤치마크** `Web Agent Benchmark` 〔신조〕 — 정해진 사이트에서 주어진 일을 해내는지 재는 시험 묶음. 실제 웹은 계속 바뀌어서 재현이 어렵고, 그래서 진짜처럼 만들어 둔 사이트를 쓰는 쪽이 표준이 되었다. <sub>생긴 때: 2023년 이후 쓰인다</sub>
- **WebArena** `WebArena` 〔신조〕 — 쇼핑몰과 게시판과 협업 도구를 실제처럼 만들어 두고 그 안에서 일을 끝내게 하는 평가. 진짜 사이트가 아니라 매번 같은 상태에서 시작할 수 있고, 그래서 점수를 견줄 수 있다. <sub>생긴 때: 2023년 무렵 나왔다</sub>
- **OSWorld** `OSWorld` 〔신조〕 — 진짜 운영체제 화면에서 파일과 프로그램을 직접 다뤄 일을 끝내게 하는 평가. 웹에 갇히지 않는 대신 환경을 되돌리는 일이 무겁고, 아직 성공률이 낮게 나온다. <sub>생긴 때: 2024년 무렵 나왔다</sub>
- **재현 가능한 환경** `Reproducible Environment` — 같은 상태에서 다시 시험할 수 있게 고정한 환경. 실제 사이트로 재면 결과를 비교할 수 없다.
- **부분 완료** `Partial Completion` — 일부만 해낸 상태. 성공과 실패로만 재면 진전을 못 본다.
- **안전 위반** `Safety Violation` — 하면 안 될 조작을 한 횟수. 성공률과 별개로 반드시 재야 하는 값이다.

## 자주 헷갈리는 짝

- **컴퓨터 사용과 API 호출** 같은 점은 둘 다 바깥 시스템을 다룬다는 것.
다른 점은 통로다. API가 있으면 언제나 그쪽이 낫다.
- **화면 캡처와 접근성 트리** 같은 점은 둘 다 화면 상태를 알려 준다는 것.
다른 점은 정확도와 비용이다. 뒤쪽이 가볍고 정확하다.
- **RPA와 컴퓨터 사용 에이전트** 같은 점은 둘 다 화면을 조작한다는 것.
다른 점은 순서를 미리 정하는가다. 35장의 워크플로와 에이전트 구별과 같다.
- **좌표 지목과 요소 지목** 같은 점은 둘 다 대상을 가리킨다는 것.
다른 점은 화면이 바뀌었을 때다. 요소 쪽이 훨씬 안 깨진다.
- **헤드리스와 화면 있는 실행** 같은 점은 둘 다 브라우저를 돌린다는 것.
다른 점은 그리는가다. 사람이 지켜보려면 그려야 한다.

## 지금 움직이는 것

이미지만 보고 좌표를 찍는 방식에서 구조 정보를 함께 쓰는 방식으로 옮겨 가고 있다. 정확도와 비용이 둘 다 나아져서다. 동시에 이 방식이 위험하다는 인식이 자리 잡으면서, 되돌릴 수 없는 조작 앞에 사람을 두는 구성이 기본값이 되었다. 그리고 사이트 쪽에서 에이전트 접근을 어떻게 다룰지가 새 논의로 올라왔다. 막을 것인가, 별도 통로를 열 것인가.
