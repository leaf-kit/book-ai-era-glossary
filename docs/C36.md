# 36장 도구와 프로토콜

<sub>7부 에이전트 · 표제어 82개 · 도해 4개</sub>

> **여는 지도** — 이 장의 낱말 여든둘. 도구 하나가 불리기까지 여섯 자리와 그것을 규격으로 묶는 두 층

이 장은 모델이 바깥 세상을 만지는 통로를 다룬다. 모델 자체는 텍스트를 만들 뿐이다. 파일을 읽지도 못하고 검색하지도 못한다. 그 텍스트를 실제 동작으로 바꿔 주는 장치가 도구다.

구조는 단순하다. 어떤 도구가 있는지 설명을 주면 모델이 어느 것을 어떤 인자로 부를지 정해서 정해진 형식으로 적는다. 그것을 프로그램이 읽어 실제로 실행하고 결과를 돌려준다. 모델이 하는 일은 여기까지이고, 실행은 언제나 바깥에서 한다.

이 구별이 중요하다. 모델이 파일을 지운 것이 아니라 프로그램이 모델의 말을 보고 파일을 지운 것이다. 그래서 안전은 모델을 잘 정렬하는 것이 아니라 실행부에 무엇을 허용할지로 정해진다. 9장의 최소 권한이 여기서 다시 나오는 이유다.

## 표제어

### 도구를 정의하기

#### 도구 사용

<sub>Tool Use</sub>

**모델이 바깥 기능을 불러 쓰는 것. 그리고 그것을 가능하게 만든 구조.**

<sub>관련어 함수 호출, 도구 스키마, 도구 결과, MCP</sub>

- **도구 스키마** `Tool Schema` — 도구가 무엇을 하고 어떤 인자를 받는지 기계가 읽을 수 있는 형식으로 적은 정의. <sub>관련어 함수 호출, 스키마(4장), 제약 디코딩(27장), 도구 설명</sub>
- **도구 이름** `Tool Name` — 모델이 부를 때 쓰는 식별자. 무엇을 하는지 짐작되게 짓는 것이 좋다.
- **도구 설명** `Tool Description` — 언제 이 도구를 쓰는지 적은 글. 실제로는 이것이 성능을 가장 크게 좌우한다.
- **인자** `Parameter` — 도구에 넘기는 값. 6장의 함수 인자와 같은 뜻이고 4부의 학습 파라미터와 다르다.
- **필수 인자** `Required Parameter` — 반드시 있어야 하는 값. 모델이 모르면 사용자에게 되물어야 하는데 그냥 지어내는 경우가 있다.
- **반환 형식** `Return Format` — 도구가 돌려주는 값의 모양. 일정해야 모델이 다음 판단을 안정되게 한다.
- **도구 예시** `Tool Example` — 올바른 호출의 본보기. 31장의 퓨샷을 도구에 적용한 것이고 효과가 크다.

### 모델에게 알리고 고르게 하기

- **함수 호출** `Function Calling` — 모델이 정해진 형식으로 어떤 함수를 어떤 인자로 부를지 적어 내놓는 기능. <sub>관련어 도구 스키마, 병렬 호출, 도구 선택, 구조화 출력(27장)</sub>
- **도구 목록 주입** `Tool Injection` — 쓸 수 있는 도구들의 정의를 프롬프트에 넣는 일. 도구가 많으면 이것만으로 수천 토큰이 든다.
- **도구 선택** `Tool Selection` — 여러 도구 중 무엇을 부를지 정하는 일. 개수가 늘수록 정확도가 떨어진다는 관찰이 있다.
- **도구 개수 한계** `Tool Count Limit` 〔신조〕 — 도구가 많아지면 고르기가 어려워지는 문제. 수십 개를 넘으면 눈에 띄게 나빠져서 무리로 나눠 단계적으로 보여 주는 방식을 쓴다. <sub>생긴 때: 2024년 이후 실무 문제로 다뤄진다</sub>
- **병렬 호출** `Parallel Tool Calls` — 한 번에 여러 도구를 부르는 것. 시간이 줄고 실패 처리가 복잡해진다.
- **호출 안 함** `No Tool Call` — 도구가 필요 없다고 판단하고 그냥 답하는 것. 이 판단이 잘못되면 아는 척하고 지어낸다.
- **강제 호출** `Forced Tool Use` — 반드시 특정 도구를 부르게 하는 설정. 형식을 보장해야 할 때 쓴다.
- **인자 생성 오류** `Argument Error` — 형식은 맞는데 값이 틀린 호출. 날짜 형식이나 식별자를 지어내는 경우가 흔하다.
- **환각 도구** `Hallucinated Tool` — 없는 도구를 부르려 하는 것. 제약 디코딩으로 막을 수 있다.

### 어디서 어떤 권한으로 실행하나

#### 샌드박스

<sub>Sandbox</sub>

**도구를 실행하는 격리된 환경. 밖으로 못 나가게 막아 둔다.**

<sub>관련어 컨테이너(8장), 최소 권한(9장), 네트워크 격리, 실행 권한</sub>

- **실행 권한** `Execution Permission` — 도구가 무엇을 할 수 있는지 정한 것. 읽기만, 특정 폴더만, 특정 명령만 같은 식으로 좁힌다.
- **네트워크 격리** `Network Isolation` — 샌드박스 안에서 나갈 수 있는 곳을 제한하는 일. 허용 목록 방식이 안전하다.
- **자원 제한** `Resource Limit` — 메모리와 계산 시간과 디스크 사용의 상한. 8장의 자원 제한 장치를 쓴다.
- **타임아웃 (도구)** `Tool Timeout` — 도구가 정해진 시간 안에 안 끝나면 끊는 설정. 없으면 에이전트가 그 자리에서 멈춘다.
- **읽기 전용 모드** `Read-Only Mode` — 쓰기를 아예 막고 읽기만 허용하는 설정. 되돌릴 수 없는 행동을 없애는 가장 단순한 방법이다.
- **허용 목록** `Allowlist` — 허용할 것을 나열하는 방식. 막을 것을 나열하는 방식보다 안전하다. 빠뜨린 것이 허용되지 않기 때문이다.
- **임시 작업 공간** `Ephemeral Workspace` — 작업이 끝나면 통째로 버리는 실행 공간. 남는 것이 없어 다음 작업에 영향을 안 준다.
- **권한 위임** `Delegated Authority` 〔신조〕 — 사용자의 권한 일부를 에이전트가 대신 쓰게 하는 것. 9장의 위임 표준이 이 자리에서 다시 필요해졌다. <sub>생긴 때: 2024년 이후 문제로 다뤄진다</sub>
- **자격 증명 분리** `Credential Isolation` — 에이전트가 열쇠 자체를 보지 못하게 하고 실행부만 갖게 하는 구성. 47장의 유출을 막는 기본 설계다.

### 결과를 돌려주기

- **도구 결과** `Tool Result` — 도구를 실행하고 돌려받은 값. 문맥에 넣어 다음 판단의 재료로 쓴다. <sub>관련어 결과 요약(32장), 오류 반환, 간접 주입(47장에서 다룬다), 신뢰 경계(32장)</sub>
- **오류 반환** `Error Handling in Tools` — 도구가 실패했을 때 무엇을 어떻게 돌려줄지 정하는 것. <sub>관련어 도구 결과, 재시도, 자기 수정(37장에서 다룬다)</sub>
- **구조화된 오류** `Structured Error` — 오류 종류와 원인과 다음 행동 제안을 형식에 맞춰 돌려주는 것. 모델이 알아듣기 쉽다.
- **부분 성공** `Partial Success` — 일부만 된 상태. 무엇이 되고 무엇이 안 되었는지 나눠 알려야 한다.
- **결과 크기 제한** `Output Size Limit` — 도구 결과의 최대 길이. 넘으면 잘라내고 잘렸다는 표시를 남긴다.
- **페이지 나누기** `Pagination` — 큰 결과를 나눠 돌려주고 필요하면 다음 것을 요청하게 하는 방식. 문맥을 아낀다.
- **멱등 도구** `Idempotent Tool` — 여러 번 불러도 결과가 같은 도구. 4장의 멱등성이 여기서 재시도를 안전하게 만든다.

### 표준으로 묶기

#### MCP 〔신조〕

<sub>Model Context Protocol</sub>

**모델과 바깥 도구 사이를 잇는 방식을 정한 공개 규격.**

갈리는 자리 — 규격이 빠르게 바뀌고 있어 판본에 따라 세부가 다르다

생긴 때 — 2024년에 공개되었다

<sub>관련어 명세(0장), 서버, 클라이언트, 공급망 공격(47장에서 다룬다)</sub>

- **MCP 서버** `MCP Server` 〔신조〕 — 도구와 자료를 규격에 맞춰 제공하는 쪽. 로컬에서 돌기도 하고 원격에 있기도 한다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **MCP 클라이언트** `MCP Client` 〔신조〕 — 서버에 연결해 도구 목록을 받아 모델에게 알리는 쪽. 대개 에이전트 실행부가 이 역할을 한다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **리소스** `Resource` 〔유동〕 — 규격에서 모델이 읽을 수 있게 제공하는 자료. 도구와 달리 부작용이 없다는 것이 구별점이다.
- **프롬프트 템플릿 (규격)** `Prompt (MCP)` 〔신조〕 — 서버가 미리 만들어 제공하는 프롬프트 조각. 자주 쓰는 지시를 서버 쪽에 두는 방식이다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **도구 발견** `Tool Discovery` — 어떤 도구가 있는지 실행 중에 알아내는 절차. 미리 다 알려 주지 않아도 되게 만든다.
- **컴퓨터 사용 규격** `Computer Use API` 〔신조〕 — 화면을 보고 마우스와 키보드를 다루게 하는 인터페이스. 40장에서 자세히 다룬다. <sub>생긴 때: 2024년 이후 쓰인다</sub>

### 규격의 안쪽

- **전송** `Transport` 〔신조〕 — 규격의 메시지를 실제로 어떤 통로로 주고받을지 정한 부분. <sub>생긴 때: 2024년 이후 이 맥락에서 쓰인다 · 관련어 표준 입출력(3장), HTTP(4장), 규격 연결, MCP</sub>
- **표준 입출력 전송** `Stdio Transport` 〔신조〕 — 같은 기계에서 서버를 프로세스로 띄우고 표준 입출력으로 주고받는 방식. 인증이 필요 없고 그 기계의 권한을 그대로 쓴다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **원격 전송** `Remote Transport` 〔신조〕 — HTTP 위에서 주고받는 방식. 여러 사용자가 한 서버를 나눠 쓸 수 있고 인증과 격리가 필요해진다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **규격 연결** `Protocol Session` 〔신조〕 — 클라이언트와 서버가 연결을 맺고 유지하는 동안의 상태. 도구 목록과 권한이 이 연결에 매인다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **능력 협상** `Capability Negotiation` 〔신조〕 — 연결을 맺을 때 양쪽이 무엇을 할 수 있는지 서로 알리고 공통분모를 정하는 절차. <sub>생긴 때: 2024년 이후 이 맥락에서 쓰인다 · 관련어 프로토콜 버전, 하위 호환(0장), 규격 연결, 초기화</sub>
- **연결 초기화** `Initialization Handshake` 〔신조〕 — 연결을 맺을 때 판본과 능력을 주고받는 첫 절차. 4장의 핸드셰이크가 이 층에서 반복된다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **프로토콜 버전** `Protocol Version` 〔신조〕 — 규격의 판본. 날짜로 적는 방식이 널리 쓰이고, 자주 바뀌어서 클라이언트와 서버의 판본이 어긋나는 일이 잦다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **기본 요소** `Primitives` 〔신조〕 — 규격이 정한 제공 단위. 실행되는 것, 읽히는 것, 미리 만들어 둔 지시 셋으로 나뉜다. <sub>생긴 때: 2024년 이후 쓰인다 · 관련어 도구 사용, 리소스, 프롬프트 템플릿 (규격), 신뢰 경계(32장)</sub>
- **루트** `Roots` 〔신조〕 — 클라이언트가 서버에게 알려 주는 접근 가능 범위. 어느 폴더까지 볼 수 있는지를 서버가 아니라 클라이언트가 정한다는 것이 요점이다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **샘플링 (규격)** `Sampling` 〔신조〕 — 서버가 클라이언트에게 모델 호출을 대신 해 달라고 요청하는 기능. <sub>갈리는 자리: 27장의 표집과 한국어로 같은 낱말이고 완전히 다른 것이다 · 생긴 때: 2024년 이후 쓰인다 · 관련어 표집(27장), 자격 증명 분리, 승인(35장)</sub>
- **이끌어내기** `Elicitation` 〔신조〕 — 서버가 진행 중에 사용자에게 추가 정보를 물어보는 기능. 미리 다 받지 않고 필요할 때 묻게 한다. <sub>생긴 때: 2025년 무렵 규격에 들어왔다</sub>
- **알림** `Notification` 〔신조〕 — 답을 기대하지 않고 한쪽이 보내는 메시지. 도구 목록이 바뀌었다는 소식이 대표적이다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **진행 알림** `Progress Notification` 〔신조〕 — 오래 걸리는 작업이 어디까지 왔는지 중간에 알리는 것. 없으면 멈춘 것과 구별이 안 된다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **요청 취소** `Request Cancellation` 〔신조〕 — 진행 중인 요청을 중단하라고 알리는 것. 사용자가 멈췄을 때 서버 쪽 작업도 같이 멈추게 한다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **서버 레지스트리** `Server Registry` 〔신조〕 — 쓸 수 있는 서버를 모아 놓고 찾을 수 있게 한 목록. 어디서 온 것인지 확인하는 절차가 같이 있어야 한다. <sub>생긴 때: 2025년 무렵부터 논의된다</sub>
- **원격 서버 인증** `Remote Server Authorization` 〔신조〕 — 원격 서버를 쓸 때 사용자를 대신해 권한을 넘기는 절차. 9장의 위임 표준을 이 층에 맞춘 것이고 세부가 계속 바뀐다. <sub>생긴 때: 2025년 무렵 규격에 들어왔다</sub>
- **서버 출처 확인** `Server Provenance` 〔신조〕 — 그 서버를 누가 만들었고 안 바뀌었는지 확인하는 일. 7장의 공급망 문제가 이 층에서 반복된다. <sub>생긴 때: 2025년 무렵부터 논의된다</sub>

### 에이전트끼리 주고받기

#### A2A 〔신조〕

<sub>Agent-to-Agent Protocol</sub>

**에이전트가 다른 에이전트에게 일을 맡기고 결과를 받는 방식을 정한 규격.**

갈리는 자리 — 특정 규격을 가리키기도 하고 에이전트 사이 통신 전반을 가리키기도 한다

생긴 때 — 2025년 무렵부터 이름이 쓰인다

<sub>관련어 에이전트 카드, 과업 상태, MCP, 멀티 에이전트(38장에서 다룬다)</sub>

- **에이전트 카드** `Agent Card` 〔신조〕 — 그 에이전트가 무엇을 할 수 있고 어떻게 부르는지 적어 공개하는 문서. <sub>생긴 때: 2025년 무렵부터 쓰인다 · 관련어 A2A, 에이전트 발견, 도구 스키마, 모델 카드(49장에서 다룬다)</sub>
- **에이전트 발견** `Agent Discovery` 〔신조〕 — 쓸 수 있는 에이전트를 찾아내는 절차. 정해진 자리에 카드를 두는 방식과 목록 서비스를 두는 방식이 논의된다. <sub>생긴 때: 2025년 무렵부터 쓰인다</sub>
- **과업 상태** `Task State` 〔신조〕 — 맡긴 일이 지금 어느 단계인지 나타내는 값. <sub>생긴 때: 2025년 무렵부터 쓰인다 · 관련어 A2A, 스트리밍 갱신, 되묻기(38장), 종료 조건(35장)</sub>
- **산출물 (A2A)** `Artifact` 〔신조〕 — 맡긴 일의 결과로 돌아오는 물건. 글일 수도 파일일 수도 있고, 7장의 빌드 산출물과 이름만 같다. <sub>생긴 때: 2025년 무렵부터 쓰인다</sub>
- **스트리밍 갱신** `Streaming Update` 〔신조〕 — 진행 중인 일의 중간 결과를 이어서 보내는 것. 4장의 SSE 위에서 도는 경우가 많다. <sub>생긴 때: 2025년 무렵부터 쓰인다</sub>
- **푸시 알림 (A2A)** `Push Notification` 〔신조〕 — 연결이 끊긴 뒤에도 결과를 알릴 수 있게 미리 받을 주소를 정해 두는 방식. 아주 오래 걸리는 일에 필요하다. <sub>생긴 때: 2025년 무렵부터 쓰인다</sub>
- **불투명 실행** `Opaque Execution` 〔신조〕 — 상대가 안에서 무엇을 어떻게 하는지 안 드러내는 성질. 남의 에이전트를 부르는 것을 전제한 설계라 그렇다. <sub>생긴 때: 2025년 무렵부터 쓰인다</sub>
- **에이전트 신뢰** `Agent Trust` 〔신조〕 — 남의 에이전트가 시킨 대로 하고 결과가 맞는지 어떻게 믿을 것인가의 문제. 규격이 풀어 주지 않는 자리이고 47장과 49장의 영역이다. <sub>생긴 때: 2025년 무렵부터 논의된다</sub>

**무엇을 잇는 규격인가로 나누면**

| 규격 | 무엇과 무엇을 잇나 | 한 번의 성격 | 누가 정의하나 |

|---|---|---|---|

| 함수 호출 | 모델과 내 코드 | 즉시 답한다 | 모델 제공자 |

| MCP | 클라이언트와 도구 서버 | 대개 짧다 | 공개 규격 |

| A2A | 에이전트와 에이전트 | 오래 걸린다 | 공개 규격 |

| HTTP API | 프로그램과 프로그램 | 즉시 답한다 | 각 서비스 |

가르는 기준이 둘이다. 한 번의 호출이 오래 걸리는가,
그리고 상대의 속을 아는가.
오래 걸리고 속을 모르면 상태와 알림과 되묻기가 필요해지고,
그래서 규격이 두꺼워진다.

- **도구 레지스트리** `Tool Registry (Shared)` 〔신조〕 — 쓸 수 있는 서버와 도구를 모아 놓은 목록. 어디서 온 것인지 확인하는 절차가 같이 필요하다. <sub>생긴 때: 2024년 이후 쓰인다</sub>

### 자주 쓰는 도구들

**도구를 성격으로 나누면**

| 성격 | 예 | 되돌릴 수 있나 | 승인 필요 |

|---|---|---|---|

| 조회 | 검색, 파일 읽기, 조회 질의 | 해당 없음 | 대개 불필요 |

| 계산 | 코드 실행, 계산기 | 해당 없음 | 샌드박스 필요 |

| 생성 | 파일 쓰기, 문서 만들기 | 대개 가능 | 경우에 따라 |

| 변경 | 데이터 수정, 설정 바꾸기 | 준비하면 가능 | 필요 |

| 외부 발신 | 메일, 메시지, 결제 | 불가능 | 반드시 |

아래로 갈수록 위험하다.
이 분류가 승인 정책의 출발점이 된다.
그리고 조회 도구도 안전하지 않다. 읽어 온 내용이 주입 통로가 되고,
읽을 수 있는 범위가 넓으면 그 자체가 유출이다.

- **검색 도구** `Search Tool` — 웹이나 사내 문서를 찾는 도구. 33장의 검색을 도구로 둔 것이다.
- **코드 실행 도구** `Code Execution Tool` — 모델이 만든 코드를 돌려 결과를 얻는 도구. 계산과 데이터 처리에 강하고 격리가 필수다.
- **파일 도구** `File Tool` — 파일을 읽고 쓰고 찾는 도구. 39장의 코딩 에이전트의 기본 도구다.
- **브라우저 도구** `Browser Tool` — 웹페이지를 열고 조작하는 도구. 40장에서 자세히 다룬다.
- **데이터베이스 도구** `Database Tool` — 질의를 실행해 결과를 얻는 도구. 읽기 전용 계정으로 두는 것이 기본이다.
- **API 도구** `API Tool` — 바깥 서비스를 부르는 도구. 인증과 속도 제한을 실행부가 다뤄야 한다.
- **하위 에이전트 도구** `Subagent as Tool` 〔신조〕 — 다른 에이전트를 하나의 도구처럼 부르는 구성. 38장에서 자세히 다룬다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **메모리 도구** `Memory Tool` 〔신조〕 — 기억을 저장하고 꺼내는 도구. 37장의 기억을 도구로 만든 것이다. <sub>생긴 때: 2024년 이후 쓰인다</sub>

### 무엇이 잘못될 수 있나

- **과도한 권한** `Excessive Permission` — 필요 이상으로 넓게 준 권한. 사고가 났을 때 피해 크기를 정한다.
- **혼동된 대리인** `Confused Deputy` 〔신조〕 — 권한을 가진 프로그램이 남의 지시를 대신 수행해 버리는 오래된 보안 문제. 에이전트가 정확히 이 구조라 다시 주목받는다. <sub>생긴 때: 오래된 개념이고 2023년 이후 에이전트 맥락에서 다시 쓰인다</sub>
- **도구 연쇄 위험** `Tool Chaining Risk` 〔신조〕 — 개별로는 안전한 도구들이 이어지면서 위험해지는 것. 읽기와 발신을 둘 다 주면 유출 경로가 완성된다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **도구 설명 조작** `Tool Poisoning` 〔신조〕 — 도구 설명에 숨은 지시를 넣어 모델을 조종하는 공격. 남이 만든 서버를 붙일 때 생긴다. <sub>생긴 때: 2024년 이후 보고된다</sub>
- **감사 기록** `Audit Trail` — 어느 도구를 어떤 인자로 언제 불렀는지 남기는 기록. 사고 뒤에 무슨 일이 있었는지 아는 유일한 방법이다.
- **정책 엔진** `Policy Engine` 〔신조〕 — 도구 호출을 허용할지 규칙으로 판단하는 층. 모델 밖에 두어 모델이 바뀌어도 규칙이 유지되게 한다. <sub>생긴 때: 2024년 이후 제품에 들어간다</sub>

## 자주 헷갈리는 짝

- **도구 사용과 함수 호출** 거의 같은 것을 다르게 부르는 이름이다.
뒤쪽이 형식과 구현을 가리키는 쪽에 가깝다.
- **도구와 리소스** 같은 점은 둘 다 모델이 쓰는 것.
다른 점은 부작용이다. 리소스는 읽기만 하고 아무것도 바꾸지 않는다.
- **샌드박스와 권한** 같은 점은 둘 다 할 수 있는 일을 제한한다는 것.
다른 점은 층이다. 앞은 환경이고 뒤는 규칙이다. 둘 다 필요하다.
- **도구 결과와 사용자 입력** 같은 점은 둘 다 신뢰할 수 없는 입력이라는 것.
다른 점은 없다. 그것이 47장의 전제다.
- **MCP와 API** 같은 점은 둘 다 기능을 노출하는 규격이라는 것.
다른 점은 대상이다. 앞은 모델이 알아듣게 설명까지 포함한다.
- **MCP와 A2A** 같은 점은 둘 다 바깥을 부르는 공개 규격이라는 것.
다른 점은 상대다. 앞은 도구를, 뒤는 다른 에이전트를 부른다.
그래서 뒤쪽에는 오래 걸리는 일의 상태와 되묻기가 들어 있다.
- **도구와 기본 요소** 같은 점은 둘 다 서버가 제공하는 것.
다른 점은 누가 고르는가다. 모델이 고르면 도구이고 사람이 고르면 자료나 프롬프트다.
- **샘플링 (규격)과 표집 (디코딩)** 한국어로 겹치는 낱말이다.
앞은 서버가 클라이언트에게 모델 호출을 부탁하는 기능이고
뒤는 27장에서 다음 토큰을 뽑는 방식이다.
- **표준 입출력 전송과 원격 전송** 같은 점은 둘 다 같은 규격을 나른다는 것.
다른 점은 인증과 격리가 필요한가다. 같은 기계 안이면 그 기계 권한을 그대로 쓴다.
- **에이전트 카드와 모델 카드** 같은 점은 둘 다 무엇인지 적어 공개하는 문서라는 것.
다른 점은 독자다. 앞은 기계가 읽는 명세이고 뒤는 49장에서 사람이 읽는 설명이다.

## 지금 움직이는 것

도구를 붙이는 방식이 표준으로 모이는 중이다. 회사마다 다르던 형식이 규격 하나로 수렴하면서 도구를 한 번 만들면 여러 곳에서 쓸 수 있게 되었다. 그와 함께 남이 만든 서버를 붙이는 위험이 새 문제로 올라왔다. 7장의 의존성과 공급망 이야기가 이 층에서 그대로 반복되고 있고, 서명과 출처 확인 같은 장치가 논의되고 있다.

## 더 볼 곳

여러 걸음을 잇는 장치가 37장이다. 도구를 통해 들어오는 공격은 47장, 실제 사례는 39장과 40장에서 다룬다.
