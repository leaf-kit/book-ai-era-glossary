# 44장 비용과 속도

<sub>8부 만들고 운영하기 · 표제어 48개 · 도해 3개</sub>

> **여는 지도** — 이 장의 낱말 마흔여덟. 돈과 시간이라는 두 축과 그것을 움직이는 손잡이들

이 장은 돈과 시간을 다룬다. 8부의 다른 장들이 만든 선택이 여기서 숫자가 된다.

두 축이 서로 밀어낸다. 배치를 키우면 싸지고 느려진다. 큰 모델을 쓰면 잘하고 비싸고 느리다. 30장의 오래 생각하기는 정확해지고 비싸고 느리다. 어느 지점을 고를지가 서비스의 성격을 정한다.

계산의 출발점은 22장의 토큰이다. 요금이 글자 수가 아니라 토큰 수로 매겨지고, 언어에 따라 같은 내용의 토큰 수가 다르다. 그래서 한국어 서비스의 비용 구조가 영어와 다르다.

그리고 최근에 항목이 하나 늘었다. 30장의 사고 토큰이다. 사용자에게 안 보이는데 요금에는 들어간다. 비용을 세는 방식이 그만큼 복잡해졌다.

## 한눈에 보기

| 무리 | 무엇을 다루나 | 어디서 다시 쓰나 |
|---|---|---|
| 비용 구조 | 무엇에 얼마가 드나 | 22장 토큰 |
| 지연 구조 | 시간이 어디서 가나 | 41장 서빙 |
| 줄이는 방법 | 어느 손잡이를 만지나 | 28장, 32장 |

| 사업 관점 | 남는 장사인가 | 50장 하드웨어 |
| 직접 돌리기 | 사는 것과 빌리는 것 | 8장 클라우드 |


## 표제어

### 무엇에 얼마가 드나

#### 토큰 비용

<sub>Token Cost</sub>

**모델을 부를 때 드는 요금. 주고받은 토큰 수로 매겨진다.**

<sub>관련어 입력 토큰, 출력 토큰, 사고 토큰, 토큰(22장), 프롬프트 캐시</sub>

- **입력 토큰** `Input Token` — 모델에 넣은 토큰. 프롬프트 전체가 여기 들어간다.
- **출력 토큰** `Output Token` — 모델이 만들어 낸 토큰. 대개 입력보다 몇 배 비싸다.
- **캐시 읽기 토큰** `Cached Input Token` 〔신조〕 — 캐시에서 재사용된 입력 토큰. 보통 입력보다 훨씬 싸게 매겨진다. <sub>생긴 때: 2024년 이후 요금 항목으로 나온다</sub>
- **캐시 쓰기** `Cache Write` 〔신조〕 — 캐시에 올리는 데 드는 비용. 한 번 쓰고 여러 번 읽어야 이득이 난다. <sub>생긴 때: 2024년 이후 요금 항목으로 나온다</sub>
- **이미지 토큰 비용** `Image Token Cost` — 이미지 하나가 차지하는 토큰 수. 해상도에 따라 크게 달라지고 29장에서 정의했다.
- **오디오 비용** `Audio Cost` — 음성 입출력에 매겨지는 요금. 초 단위로 매겨지기도 해서 토큰과 단위가 다르다.
- **단가** `Unit Price` — 토큰 백만 개당 요금으로 적는 것이 관행이다. 모델과 시점에 따라 다르고 자주 바뀐다.
- **요금 변동** `Price Change` — 단가가 시간에 따라 바뀌는 것. 지난 몇 해 동안 같은 수준의 성능이 크게 싸졌다.

### 시간이 어디서 가나

**응답 시간을 이루는 조각들**

| 조각 | 무엇 때문에 | 줄이는 방법 |

|---|---|---|

| 네트워크 왕복 | 거리와 연결 수립 | 가까운 리전, 연결 재사용 |

| 대기열 | 앞에 밀린 요청 | 용량, 우선순위 |

| 프리필 | 입력이 길다 | 프롬프트 줄이기, 캐시 |

| 디코드 | 출력이 길다 | 출력 제한, 작은 모델 |

| 사고 | 답하기 전 계산 | 사고 예산 |

| 도구 왕복 | 바깥 호출 대기 | 병렬 호출, 캐시 |

에이전트에서는 마지막 줄이 지배적인 경우가 많다.
모델은 빠른데 도구가 느려서 전체가 느리다.
어디서 시간이 가는지는 43장의 시간 분해로 확인한다.

- **첫 토큰 지연** `Time to First Token, TTFT` — 요청을 보내고 첫 글자가 나오기까지의 시간. <sub>관련어 토큰당 지연, 프롬프트 캐시, 대기열 길이(41장), 스트리밍(41장)</sub>
- **토큰당 지연** `Time Per Output Token, TPOT` — 토큰 하나를 만드는 데 걸리는 평균 시간. 읽는 속도로 느껴진다. 사람이 읽는 속도보다 빠르면 더 빨라도 체감 차이가 작다.
- **전체 응답 시간** `End-to-End Latency` — 요청부터 마지막 글자까지의 시간. 자동화된 처리에서는 이 값이 중요하고 대화에서는 첫 토큰이 더 중요하다.
- **꼬리 지연 (모델)** `Tail Latency` — 느린 쪽 몇 퍼센트의 응답 시간. 평균이 좋아도 이것이 나쁘면 사용자는 느리다고 느낀다.
- **도구 왕복** `Tool Round-Trip` — 도구를 부르고 결과를 받기까지의 시간. 에이전트에서 전체 시간의 대부분을 차지하기도 한다.
- **병렬 호출 이득** `Parallel Call Gain` — 서로 무관한 도구를 동시에 불러 시간을 줄이는 것. 36장의 병렬 호출이 여기서 값을 한다.
- **체감 속도** `Perceived Latency` — 사용자가 느끼는 빠르기. 실제 시간보다 첫 반응과 진행 표시에 좌우된다.
- **진행 표시** `Progress Indicator` — 무언가 하고 있다는 것을 보여 주는 것. 오래 걸리는 작업에서 체감을 크게 바꾼다.

### 줄이는 손잡이

#### 프롬프트 캐시 〔신조〕

<sub>Prompt Caching</sub>

**여러 요청이 공유하는 앞부분의 계산 결과를 저장해 두고 다시 쓰는 것.**

생긴 때 — 2023년 이후 요금 체계에 들어왔다

<sub>관련어 접두 캐시(41장), 캐시 정렬(32장), 고정 구간(32장), 첫 토큰 지연</sub>

- **정확 일치 캐시** `Exact Match Cache` — 같은 요청이 오면 이전 답을 그대로 주는 것. 안전하고 적중률이 낮다.
- **출력 길이 제한** `Output Length Limit` — 답의 길이를 제한하는 설정. 출력 단가가 비싸서 효과가 크고, 잘리면 안 되는 자리를 조심해야 한다.
- **프롬프트 다이어트** `Prompt Trimming` — 프롬프트에서 불필요한 부분을 걷어 내는 일. 32장의 예산 관리가 이 작업이다.
- **검색 결과 개수 조절** `Retrieval Count Tuning` — 넣는 근거 개수를 줄이는 것. 33장에서 말한 대로 개수가 품질과 늘 비례하지 않는다.
- **사고 예산 조절** `Reasoning Budget Control` 〔신조〕 — 얼마나 생각하게 할지 조절하는 것. 30장의 낱말이고 여기서는 비용 손잡이다. <sub>생긴 때: 2024년 이후 설정으로 제공된다</sub>
- **양자화 (비용)** `Quantization for Cost` — 직접 돌릴 때 정밀도를 낮춰 처리량을 올리는 것. 28장의 방법이 여기서 요금 절감이 된다.
- **배칭 (비용)** `Batching for Cost` — 묶어 처리해 같은 자원으로 더 많이 처리하는 것. 41장에서 정의했다.

### 무엇을 세고 나누나

- **단위 경제** `Unit Economics` — 한 번의 요청이나 한 명의 사용자에게 드는 비용과 그것으로 얻는 값의 관계. <sub>관련어 요청당 비용, 예산 상한, 비용 분해(43장), 사용량 집계(41장)</sub>
- **요청당 비용** `Cost per Request` — 한 번의 호출에 든 요금. 입력과 출력과 사고 토큰을 다 더해야 한다.
- **과업당 비용** `Cost per Task` 〔신조〕 — 에이전트가 한 과업을 끝내는 데 든 총 요금. 걸음 수가 달라 편차가 크다. <sub>생긴 때: 2024년 이후 쓰인다</sub>
- **사용자당 비용** `Cost per User` — 사용자 한 명에게 한 달에 드는 요금. 가격을 정하는 근거가 된다.
- **비용 분포** `Cost Distribution` — 사용자나 기능별 비용의 분포. 평균보다 이 그림이 절감 자리를 알려 준다.
- **지출 상한** `Spending Cap` — 쓸 수 있는 최대 금액. 요청 단위와 하루 단위와 계정 단위로 나눠 거는 것이 안전하다.
- **비용 경보** `Cost Alert` — 정해진 선을 넘으면 알리는 것. 35장의 비용 폭주를 막는 마지막 방어선이다.
- **비용 귀속** `Cost Attribution` — 어느 기능이나 어느 팀이 얼마를 썼는지 나누는 일. 태그를 붙여 두면 43장의 기록에서 바로 나온다.
- **원가율** `Cost Ratio` — 매출 대비 모델 비용의 비율. 이 값이 사업이 되는지를 정한다.
- **한계 비용** `Marginal Cost` — 사용자가 한 명 늘 때 추가로 드는 비용. 전통적인 소프트웨어와 달리 0이 아니라는 것이 이 분야의 특징이다.

### 사는 것과 빌리는 것

**남의 서비스와 직접 돌리기의 갈림**

| 항목 | 남의 서비스 | 직접 돌리기 | 판단 기준 |

|---|---|---|---|

| 초기 비용 | 없다 | 장비와 사람 | 물량 규모 |

| 단가 | 정해져 있다 | 사용률에 달렸다 | 부하가 꾸준한가 |

| 운영 부담 | 없다 | 크다 | 인력이 있는가 |

| 데이터 | 밖으로 나간다 | 안에 머문다 | 규제와 정책 |

| 모델 선택 | 제공되는 것만 | 아무거나 | 고친 모델이 필요한가 |

부하가 들쭉날쭉하면 빌리는 편이 거의 항상 싸다.
직접 돌리는 이득은 사용률이 높을 때만 난다.
가속기가 절반만 일하면 단가가 두 배가 되고, 그러면 대개 빌리는 것보다 비싸다.

- **사용률** `Utilization` — 산 자원을 실제로 얼마나 쓰는가. 직접 돌릴 때 이 값이 단가를 정한다.
- **손익 분기** `Break-Even Point` — 직접 돌리는 것이 빌리는 것보다 싸지는 물량. 계산해 보면 생각보다 큰 경우가 많다.
- **예약 할인** `Reserved Pricing` — 오래 쓰기로 약속하고 싸게 받는 것. 가속기에서 차이가 특히 크다.
- **스팟 활용** `Spot Usage` — 남는 자원을 싸게 쓰되 회수될 수 있는 방식. 끊겨도 되는 일괄 작업에 맞는다.
- **총소유비용** `Total Cost of Ownership, TCO` — 장비값만이 아니라 전기와 냉각과 사람까지 더한 비용. 직접 돌리기를 판단할 때 이것으로 계산해야 한다.
- **전환 비용** `Switching Cost` — 다른 모델이나 제공자로 옮길 때 드는 비용. 프롬프트를 다시 맞추고 평가를 다시 돌려야 한다.

### 품질과 비용의 거래

- **품질 비용 곡선** `Quality-Cost Tradeoff` — 돈을 더 쓰면 품질이 얼마나 오르는지의 관계. <sub>관련어 모델 계층화, 프롬프트 캐시, 다축 평가(42장), 사고 예산(30장)</sub>
- **충분한 품질** `Good Enough` — 그 용도에 필요한 만큼의 품질. 더 올려도 사용자가 못 느끼는 구간이 있다.
- **품질 하한** `Quality Floor` — 떨어지면 안 되는 최소 수준. 비용을 줄일 때 이 선을 먼저 정해 둔다.
- **과잉 품질** `Over-provisioning` — 필요 이상으로 좋은 모델이나 긴 사고를 쓰는 것. 가장 흔한 낭비 유형이다.
- **요청 유형 분류** `Request Classification` — 요청을 난이도나 종류로 나누는 일. 계층화의 전제이고 이 분류의 정확도가 절감 폭을 정한다.
- **점진적 최적화** `Incremental Optimization` — 한 번에 하나씩 바꾸고 재는 방식. 여러 개를 같이 바꾸면 무엇이 효과였는지 모른다.
- **비용 회귀** `Cost Regression` — 바꾼 뒤에 비용이 오른 것. 품질 회귀와 함께 봐야 한다.

## 자주 헷갈리는 짝

- **첫 토큰 지연과 전체 시간** 같은 점은 둘 다 속도라는 것.
다른 점은 무엇을 정하는가다. 대화는 앞이, 자동 처리는 뒤가 중요하다.
- **프롬프트 캐시와 시맨틱 캐시** 같은 점은 둘 다 재사용으로 아낀다는 것.
다른 점은 무엇을 재사용하는가다. 계산 결과인가 답 자체인가.
- **처리량과 비용** 같은 점은 둘 다 자원 효율과 관련된다는 것.
다른 점은 관점이다. 직접 돌릴 때는 처리량이 곧 단가다.
- **사고 토큰과 출력 토큰** 같은 점은 둘 다 만들어 낸 토큰이라는 것.
다른 점은 사용자에게 보이는가다. 보이지 않는 비용이 생겼다.
- **요청당 비용과 과업당 비용** 같은 점은 둘 다 단위 비용이라는 것.
다른 점은 에이전트에서 한 과업이 여러 요청이라는 것.

## 지금 움직이는 것

같은 성능의 단가가 계속 내려가는 흐름이 이어지고 있다. 그런데 총비용은 안 줄어드는 경우가 많다. 싸진 만큼 더 많이 쓰고, 30장의 오래 생각하기가 요청당 토큰을 늘렸기 때문이다. 그래서 비용 관리의 무게가 단가 협상에서 사용량 관리로 옮겨 갔다. 그리고 사고 토큰처럼 보이지 않는 항목이 생기면서 청구서를 미리 예측하기가 어려워졌다.

## 더 볼 곳

하드웨어 쪽 원가 구조는 50장에서 다룬다. 쓸수록 좋아지는 고리를 만드는 이야기가 45장이고, 여기서 쓴 지표의 출처는 43장이다.
