# 4장 네트워크와 프로토콜

<sub>1부 컴퓨터라는 바닥 · 표제어 59개 · 도해 3개</sub>

> **여는 지도** — 이 장의 낱말 쉰아홉. 아래에서 위로 갈수록 사람의 말에 가까워진다

이 장은 떨어져 있는 기계 둘이 말을 맞추는 규칙을 다룬다. 3장이 한 기계 안에서 프로세스끼리 이야기하는 방법이었다면, 여기는 그 사이에 선이 놓인다.

선이 놓이는 순간 세 가지가 달라진다. 첫째, 시간이 걸린다. 같은 건물 안이면 1밀리초, 대륙을 건너면 150밀리초쯤이다. 둘째, 잃어버린다. 패킷은 도중에 사라지고, 사라진 것을 알아채고 다시 보내야 한다. 셋째, 순서가 뒤바뀐다. 나중에 보낸 것이 먼저 도착한다. 이 셋을 누가 처리하는가로 계층이 갈린다.

이 장이 6부와 8부에서 계속 돌아온다. 모델을 부르는 일이 결국 HTTP 요청 하나이고, 답이 조금씩 흘러나오는 것이 여기 나오는 스트리밍이며, 요청이 몰릴 때 앞에서 막아 주는 장치가 여기 나오는 게이트웨이다. 첫 토큰까지의 지연이라는 8부의 지표도 절반은 네트워크 이야기다.

## 표제어

### 계층과 주소

#### 프로토콜

<sub>Protocol</sub>

**떨어져 있는 둘이 데이터를 주고받기로 미리 정해 놓은 약속.**

<sub>관련어 계층 모델, 패킷, 명세(0장), MCP(36장에서 다룬다)</sub>

- **계층 모델** `Layered Model` — 네트워크를 여러 층으로 나누고 층마다 맡은 일을 정한 틀. <sub>갈리는 자리: 일곱 층으로 세는 사람과 네 층으로 세는 사람이 섞여 있어 계층 번호가 어긋난다 · 관련어 프로토콜, IP, 로드 밸런서</sub>
- **패킷** `Packet` — 네트워크로 보낼 데이터를 잘라 놓은 덩어리 하나. <sub>관련어 헤더, MTU, 프레임, 페이로드</sub>
- **헤더** `Header` — 데이터 앞에 붙는 관리 정보. 계층마다 자기 헤더를 붙여서, 실제로 나가는 패킷에는 헤더가 여러 겹 쌓여 있다.
- **페이로드** `Payload` — 헤더를 뺀 실제 데이터 부분. 위층 입장에서는 이것만 보인다.
- **프레임** `Frame` — 링크 계층이 다루는 덩어리. 같은 물리 구간 안에서만 의미가 있다. 20장의 영상 프레임과 다른 낱말이다.
- **MTU** `Maximum Transmission Unit` — 한 번에 보낼 수 있는 최대 크기. 이것보다 크면 쪼개지고, 쪼개지면 하나만 잃어도 전체를 다시 보낸다.
- **IP** `Internet Protocol` — 패킷을 목적지 주소로 보내는 인터넷의 기본 규약. <sub>관련어 IPv4, IPv6, 라우팅, NAT, 서브넷</sub>
- **IPv4** `Internet Protocol version 4` — 32비트 주소를 쓰는 옛 방식. 점으로 나눈 네 숫자로 적는다. 주소가 모자란다.
- **IPv6** `Internet Protocol version 6` — 128비트 주소를 쓰는 새 방식. 콜론으로 나눈 16진수로 적는다. 주소는 넉넉한데 옮겨 가는 속도가 느리다.
- **라우팅** `Routing` — 패킷을 다음 어디로 넘길지 정하는 일. 중간 장비들이 서로 길 정보를 주고받으며 표를 만든다.
- **서브넷** `Subnet` — 주소 대역을 잘라 나눈 구역. 어디까지가 같은 구역인지를 마스크로 표시한다.
- **NAT** `Network Address Translation` — 집이나 회사 안의 여러 기기가 바깥 주소 하나를 나눠 쓰게 바꿔 주는 장치. 주소 부족을 미뤘고, 대신 바깥에서 안으로 먼저 연결하기 어렵게 만들었다.
- **MAC 주소** `Media Access Control Address` — 네트워크 장치에 붙은 하드웨어 주소. 같은 물리 구간 안에서만 쓰인다.

### 전송과 연결

#### TCP

<sub>Transmission Control Protocol</sub>

**잃어버린 패킷을 다시 보내고 순서를 맞춰 주는 전송 규약.**

<sub>관련어 UDP, 핸드셰이크, 혼잡 제어, QUIC, 소켓</sub>

- **UDP** `User Datagram Protocol` — 보내기만 하고 도착을 확인하지 않는 전송 규약. <sub>관련어 TCP, QUIC, DNS</sub>
- **핸드셰이크** `Handshake` — 연결을 시작하기 전에 서로 확인하는 절차. TCP는 세 번, 보안을 얹으면 몇 번 더 오간다.
- **혼잡 제어** `Congestion Control` — 네트워크가 막히지 않도록 보내는 속도를 조절하는 알고리즘. 여러 방식이 있고 어느 것을 쓰느냐로 성능이 달라진다.
- **흐름 제어** `Flow Control` — 받는 쪽이 감당할 만큼만 보내게 조절하는 장치. 혼잡 제어와 목적이 다르다.
- **소켓** `Socket` — 프로그램이 네트워크 연결을 다루는 통로. 주소와 포트의 짝으로 식별된다. <sub>관련어 포트, 파일 디스크립터(3장), TCP</sub>
- **포트** `Port` — 한 기계 안에서 어느 프로그램에게 갈 것인지를 구별하는 번호. 웹은 80과 443을 쓴다.
- **QUIC** `QUIC` — UDP 위에 다시 만든 전송 규약. TCP가 하던 일을 하면서 앞이 밀리는 문제를 피한다. <sub>관련어 TCP, UDP, HTTP/3</sub>

### 이름과 안전

- **DNS** `Domain Name System` — 사람이 읽는 이름을 기계가 쓰는 주소로 바꿔 주는 체계. <sub>관련어 도메인, TTL, UDP</sub>
- **도메인** `Domain` — 점으로 나눈 이름 체계. 오른쪽이 위이고 왼쪽으로 갈수록 좁아진다.
- **TTL** `Time To Live` — 답을 얼마나 기억해 둘지 정한 시간. 짧으면 반영이 빠르고 물어보는 횟수가 는다. 패킷이 몇 번까지 넘어갈 수 있는지를 뜻하기도 한다.

#### TLS

<sub>Transport Layer Security</sub>

**주고받는 내용을 엿듣지 못하게 감싸고 상대가 맞는지 확인하는 규약.**

갈리는 자리 — SSL과 TLS를 같은 뜻으로 쓰는 문서가 많다. 실제 구현은 대부분 TLS다

<sub>관련어 인증서, HTTPS, 대칭 암호(9장에서 다룬다), 종단간 암호화(9장에서 다룬다)</sub>

- **인증서** `Certificate` — 이 주소가 이 주인의 것이라고 제3자가 서명해 준 문서. 만료되면 브라우저가 경고를 띄운다.
- **HTTPS** `HTTP Secure` — HTTP를 TLS로 감싼 것. 지금은 사실상 기본값이다.

### 웹의 규약

#### HTTP

<sub>HyperText Transfer Protocol</sub>

**요청 하나에 응답 하나가 돌아오는 웹의 기본 규약.**

<sub>관련어 메서드, 상태 코드, REST, 쿠키, HTTP/2, HTTP/3</sub>

- **메서드** `Method` — 요청의 종류. 가져오기, 만들기, 바꾸기, 지우기를 구별한다. 6장의 객체 메서드와 다른 낱말이다.
- **상태 코드** `Status Code` — 응답의 결과를 나타내는 세 자리 숫자. <sub>관련어 메서드, HTTP, 재시도, 속도 제한</sub>
- **HTTP/2** `HTTP/2` — 한 연결 위에 여러 요청을 겹쳐 보내는 버전. 헤더도 압축한다. 앞의 것이 밀리면 뒤가 기다리는 문제는 남아 있다.
- **HTTP/3** `HTTP/3` — QUIC 위에서 도는 버전. 흐름끼리 서로 기다리지 않는다.
- **쿠키** `Cookie` — 서버가 브라우저에 맡겨 두고 매 요청마다 돌려받는 작은 데이터. 상태 없는 HTTP에 상태를 붙이는 오래된 방법이다.
- **CORS** `Cross-Origin Resource Sharing` — 다른 출처의 서버를 브라우저에서 부를 수 있게 허용하는 규칙. 서버가 허용한다고 응답 헤더에 적어야 브라우저가 통과시킨다.
- **REST** `Representational State Transfer` 〔유동〕 — 자원을 경로로 나타내고 메서드로 무엇을 할지 정하는 설계 방식. <sub>갈리는 자리: 원래 정의를 지키는 것만 REST라 부르는 쪽과 JSON을 주고받으면 REST라 부르는 쪽이 갈린다 · 관련어 HTTP, 메서드, gRPC, GraphQL</sub>
- **gRPC** `gRPC` — HTTP/2 위에서 함수 호출처럼 쓰도록 만든 방식. 형식을 미리 정의해서 크기가 작고 빠르다. 브라우저에서 바로 쓰기는 번거롭다.
- **GraphQL** `GraphQL` — 필요한 항목만 골라 한 번에 물어보는 질의 방식. 요청 횟수는 줄고 서버 쪽 복잡도는 는다.
- **JSON** `JavaScript Object Notation` — 데이터를 사람이 읽을 수 있는 글자로 적는 형식. <sub>관련어 직렬화, 스키마, gRPC, 구조화 출력(27장에서 다룬다)</sub>
- **직렬화** `Serialization` — 메모리에 있는 구조를 보내거나 저장할 수 있는 바이트 줄로 바꾸는 일. 반대는 역직렬화다.
- **스키마** `Schema` — 데이터가 어떤 모양이어야 하는지 미리 적어 둔 정의. 5장의 데이터베이스 스키마, 36장의 도구 스키마가 전부 같은 낱말이다.

### 흘려보내기

- **스트리밍** `Streaming` — 데이터를 다 만든 뒤에 한 번에 보내지 않고 만드는 대로 조금씩 보내는 방식. <sub>관련어 SSE, 웹소켓, 청크 전송, 첫 토큰 지연(44장에서 다룬다)</sub>

**서버가 계속 무언가를 보내는 네 가지 방법**

| 방식 | 어떻게 도나 | 어디에 맞나 |

|---|---|---|

| 폴링 | 클라이언트가 주기적으로 물어본다 | 간단하고 낭비가 있다 |

| 롱 폴링 | 물어보고 답이 생길 때까지 기다린다 | 옛 환경에서 쓴다 |

| SSE | 한 방향으로 서버가 계속 보낸다 | 모델 응답 스트리밍 |

| 웹소켓 | 양방향으로 계속 주고받는다 | 채팅, 협업 편집 |

모델 응답에 SSE가 많이 쓰이는 이유는 방향이 한쪽뿐이라서다.
양방향이 필요해지는 것은 음성 대화처럼 중간에 끼어들어야 할 때다.

- **SSE** `Server-Sent Events` — 서버에서 클라이언트로만 이어서 보내는 HTTP 방식. 보통 HTTP 위에서 돌아 중간 장비를 잘 통과한다.
- **웹소켓** `WebSocket` — HTTP로 시작해 양방향 연결로 바꾸는 방식. 연결을 계속 들고 있어야 해서 서버 자원을 더 쓴다.
- **폴링** `Polling` — 새 것이 있는지 주기적으로 물어보는 방식. 간단하지만 대부분의 요청이 빈손으로 돌아온다.

### 앞단에 놓이는 장치

- **로드 밸런서** `Load Balancer` — 들어온 요청을 여러 서버에 나눠 주는 장치. <sub>관련어 리버스 프록시, 헬스 체크, 게이트웨이(41장에서 다룬다)</sub>
- **리버스 프록시** `Reverse Proxy` — 클라이언트 앞에 서서 뒤의 서버들을 대신 상대하는 장치. 암호 해제와 캐싱과 라우팅을 여기서 한다.
- **헬스 체크** `Health Check` — 서버가 살아 있는지 주기적으로 확인하는 요청. 살아 있다는 것과 일을 받을 준비가 되었다는 것을 나눠 확인하기도 한다.
- **CDN** `Content Delivery Network` — 자주 쓰는 파일을 사용자 가까운 곳에 복사해 두는 망. 거리가 줄어 지연이 줄어든다.
- **방화벽** `Firewall` — 정해진 규칙에 맞는 통신만 통과시키는 장치. 어느 포트로 어디에서 오는 것을 허용할지 정한다.
- **속도 제한** `Rate Limiting` — 일정 시간 안에 받을 요청 수를 정해 두고 넘으면 거절하는 장치. <sub>관련어 재시도, 지수 백오프, 상태 코드, 게이트웨이(41장에서 다룬다)</sub>
- **재시도** `Retry` — 실패한 요청을 다시 보내는 일. <sub>관련어 지수 백오프, 멱등성, 타임아웃, 서킷 브레이커</sub>
- **지수 백오프** `Exponential Backoff` — 재시도 간격을 두 배씩 늘리는 방식. 무작위를 섞어야 모두가 같은 순간에 몰리는 것을 막는다.
- **멱등성** `Idempotency` — 같은 요청을 여러 번 보내도 결과가 한 번 보낸 것과 같은 성질. 이 성질이 있어야 마음 놓고 재시도할 수 있다.
- **타임아웃** `Timeout` — 정해진 시간 안에 답이 없으면 포기하는 설정. 없으면 영영 기다린다. 모델 호출처럼 오래 걸리는 요청에서 값을 잡기가 까다롭다.
- **서킷 브레이커** `Circuit Breaker` — 계속 실패하는 대상에 대해 한동안 아예 요청을 안 보내는 장치. 죽어 가는 쪽을 더 밀어붙이지 않게 한다.

**네트워크 성능을 재는 다섯 숫자**

| 숫자 | 무엇을 재나 | 무엇이 정하나 |

|---|---|---|

| 지연 | 한 번 오가는 데 걸리는 시간 | 거리와 중간 장비 수 |

| 대역폭 | 초당 나를 수 있는 양 | 회선 용량 |

| 처리량 | 실제로 나른 양 | 대역폭과 프로토콜 효율 |

| 패킷 손실 | 사라진 패킷의 비율 | 혼잡과 회선 품질 |

| 지터 | 지연이 들쭉날쭉한 정도 | 대기 줄이 쌓였다 빠지는 정도 |

대역폭은 돈으로 늘릴 수 있고 지연은 잘 안 줄어든다.
빛의 속도가 정해져 있어서다. 서울에서 미국 서부까지 왕복이 대략 150밀리초다.

- **지연** `Latency` — 요청을 보내고 답이 오기까지의 시간. 44장에서 모델 이야기로 다시 나온다.
- **RTT** `Round-Trip Time` — 한 번 갔다 오는 데 걸리는 시간. 연결을 맺는 데 몇 번의 왕복이 드는지가 첫 응답 속도를 정한다.
- **처리량** `Throughput` — 단위 시간에 실제로 처리한 양. 지연과 서로 밀어내는 관계라 둘을 같이 봐야 한다.

## 자주 헷갈리는 짝

- **지연과 대역폭** 같은 점은 둘 다 빠르기를 나타낸다는 것.
다른 점은 지연이 한 번의 왕복 시간이고 대역폭이 시간당 양이라는 것.
굵은 파이프가 짧은 파이프는 아니다.
- **TCP와 UDP** 같은 점은 둘 다 IP 위에서 도는 전송 규약이라는 것.
다른 점은 잃어버린 것을 되살리는가다. 늦은 데이터가 쓸모없으면 UDP가 낫다.
- **SSE와 웹소켓** 같은 점은 둘 다 서버가 계속 보낼 수 있다는 것.
다른 점은 방향이다. SSE는 한 방향이고 웹소켓은 양방향이다.
- **프록시와 리버스 프록시** 같은 점은 둘 다 사이에 서서 대신 요청한다는 것.
다른 점은 누구 편이냐다. 앞은 클라이언트 쪽에, 뒤는 서버 쪽에 선다.
- **TLS와 종단간 암호화** 같은 점은 둘 다 내용을 감싼다는 것.
다른 점은 서버가 내용을 볼 수 있는가다. TLS는 서버에 닿으면 풀린다.

## 지금 움직이는 것

모델 서비스가 늘면서 네트워크 앞단의 요구가 바뀌었다. 요청 하나가 몇 밀리초가 아니라 몇십 초를 잡고, 응답이 계속 흘러나오며, 제한을 요청 수가 아니라 토큰 수로 걸어야 한다. 기존 게이트웨이 제품들이 이 세 가지에 맞춰 기능을 붙이는 중이다.

## 더 볼 곳

여기서 나온 요청과 응답이 5장의 저장과 붙고, 8장에서 여러 대로 늘어난다. TLS와 인증서는 9장에서 원리가 나오고, 앞단 장치는 41장에서 모델 이야기로 돌아온다.
