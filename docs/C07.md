# 7장 만드는 도구와 협업

<sub>1부 컴퓨터라는 바닥 · 표제어 52개 · 도해 3개</sub>

> **여는 지도** — 이 장의 낱말 쉰둘. 코드 한 줄이 사용자에게 닿기까지 지나는 여섯 자리

이 장은 코드를 여럿이 같이 고치고 안전하게 내보내는 장치들을 다룬다. 기계의 이야기가 아니라 사람이 여럿이라서 생긴 이야기다.

혼자 만들면 이 장의 절반이 필요 없다. 브랜치도 리뷰도 필요 없고, 고장 나면 자기가 고치면 된다. 사람이 늘고 코드가 오래 살면 달라진다. 누가 무엇을 왜 고쳤는지 남아야 하고, 고치기 전에 남이 봐야 하고, 망가졌을 때 되돌릴 수 있어야 한다.

39장에서 이 장이 그대로 돌아온다. 코딩 에이전트가 하는 일은 결국 여기 나오는 절차 안에서 일어난다. 브랜치를 만들고, 고치고, 테스트를 돌리고, 풀 리퀘스트를 연다. 에이전트를 붙일 자리를 찾으려면 이 절차의 어느 칸이 사람의 판단을 필요로 하는지 먼저 알아야 한다.

|---|---|---|

## 표제어

### 버전 관리

#### 버전 관리

<sub>Version Control, VCS</sub>

**코드가 바뀐 기록을 전부 남기고 언제든 옛 상태로 돌아갈 수 있게 하는 장치.**

<sub>관련어 커밋, 브랜치, 병합, 해시(1장), 저장소</sub>

- **커밋** `Commit` — 한 묶음의 변경을 기록으로 확정하는 일. 그리고 그 기록 하나. <sub>관련어 브랜치, 커밋 메시지, 커밋(5장)</sub>
- **저장소** `Repository, Repo` — 코드와 그 기록 전체를 담은 하나의 단위. 저장소를 하나로 둘지 여럿으로 쪼갤지가 오래된 논쟁이다.
- **커밋 메시지** `Commit Message` — 그 커밋이 무엇을 왜 바꿨는지 적은 글. 첫 줄이 요약이고 그 아래가 이유다.
- **브랜치** `Branch` — 기록을 갈라서 본줄기와 따로 작업할 수 있게 만든 갈래. <sub>관련어 병합, 충돌, 리베이스, 트렁크 기반 개발</sub>
- **병합** `Merge` — 갈라졌던 두 갈래를 하나로 합치는 일. 같은 자리를 양쪽이 고쳤으면 충돌이 난다.
- **병합 충돌** `Merge Conflict` — 양쪽이 같은 줄을 다르게 고쳐서 자동으로 못 합치는 상태. 사람이 어느 쪽을 남길지 정해야 한다. 1장의 해시 충돌과 다른 낱말이다.
- **리베이스** `Rebase` — 내 커밋들을 최신 본줄기 위로 옮겨 붙이는 일. 기록이 깔끔해지고, 이미 공유한 커밋에 하면 남의 기록과 어긋난다.
- **체리픽** `Cherry-pick` — 다른 갈래의 커밋 하나만 골라 가져오는 일. 급한 수정을 옛 버전에 넣을 때 쓴다.
- **태그** `Tag` — 특정 커밋에 붙이는 이름표. 어느 커밋이 어느 버전인지 표시할 때 쓴다.
- **디프** `Diff` — 두 상태의 차이를 줄 단위로 보여 주는 것. 리뷰의 기본 단위이고, 39장에서 에이전트가 내놓는 결과물의 형태이기도 하다.
- **블레임** `Blame` — 각 줄을 마지막으로 고친 커밋을 표시해 주는 기능. 탓하려는 것이 아니라 맥락을 찾으려는 용도다.
- **이등분 탐색** `Bisect` — 언제부터 깨졌는지를 절반씩 줄여 가며 찾는 방법. 커밋이 천 개여도 열 번이면 찾는다.

### 여럿이 고치는 절차

- **풀 리퀘스트** `Pull Request, PR` — 내 갈래를 본줄기에 합쳐 달라고 요청하고, 그 자리에서 검토를 받는 장치. <sub>관련어 코드 리뷰, 브랜치, 승인, CI</sub>
- **코드 리뷰** `Code Review` — 합치기 전에 다른 사람이 코드를 읽고 의견을 다는 일. <sub>관련어 풀 리퀘스트, 린터, 코드 오너, 코드 리뷰 에이전트(39장에서 다룬다)</sub>
- **리뷰 승인** `Approval` — 리뷰어가 합쳐도 된다고 표시하는 일. 몇 명의 승인이 필요한지를 저장소마다 정해 둔다.
- **코드 오너** `Code Owner` — 어느 폴더의 변경은 누구의 승인을 받아야 하는지 적어 둔 규칙. 리뷰어를 자동으로 지정한다.
- **트렁크 기반 개발** `Trunk-Based Development` — 갈래를 짧게 유지하고 본줄기에 자주 합치는 방식. 충돌이 작아지는 대신 미완성 코드를 감출 장치가 필요해진다.
- **기능 플래그** `Feature Flag` — 코드는 들어가 있지만 설정으로 켜고 끄는 장치. 미완성 기능을 감추고, 문제가 나면 배포 없이 끌 수 있다.

### 안 깨졌는지 확인하기

**테스트 다섯 층과 각각이 잡는 것**

| 층 | 무엇을 확인하나 | 성격 |

|---|---|---|

| 단위 테스트 | 함수 하나가 제대로 도는가 | 빠르고 많다 |

| 통합 테스트 | 여러 부분이 붙어서 도는가 | 느리고 진짜에 가깝다 |

| 계약 테스트 | 서로 약속한 형식을 지키는가 | 시스템 사이 경계 |

| 종단 테스트 | 사용자 관점에서 되는가 | 가장 느리고 잘 깨진다 |

| 회귀 테스트 | 예전에 고친 것이 다시 깨졌는가 | 사고마다 하나씩 는다 |

아래로 갈수록 진짜에 가깝고 느리고 불안정하다.
42장에서 모델을 평가할 때 같은 층 구조가 나오는데,
거기서는 아래층이 특히 불안정해서 다루기가 더 까다롭다.

- **단위 테스트** `Unit Test` — 함수나 클래스 하나가 정해진 대로 도는지 확인하는 자동 검사. <sub>관련어 통합 테스트, 목, 커버리지</sub>
- **통합 테스트** `Integration Test` — 여러 부분을 실제로 붙여서 도는지 확인하는 검사. 진짜에 가깝고 느리다.
- **종단 테스트** `End-to-End Test, E2E` — 사용자가 하는 것과 같은 경로로 확인하는 검사. 가장 믿을 만하고 가장 잘 깨진다.
- **목** `Mock` — 진짜 대신 세워 두는 가짜 구현. 느리거나 돈이 드는 것을 대신한다.
- **픽스처** `Fixture` — 시험을 돌리기 전에 미리 만들어 두는 데이터나 상태. 매번 같은 조건에서 시작하게 만든다.
- **커버리지** `Coverage` 〔유동〕 — 테스트가 코드의 몇 퍼센트를 지나갔는지 재는 값. <sub>갈리는 자리: 줄 기준과 분기 기준이 다르고, 어느 쪽인지 안 적으면 값이 비교가 안 된다 · 관련어 단위 테스트, 회귀 테스트, 굿하트의 법칙(42장에서 다룬다)</sub>
- **회귀 테스트** `Regression Test` — 예전에 고쳤던 문제가 다시 생겼는지 확인하는 검사. 사고가 날 때마다 하나씩 늘어난다.
- **플래키 테스트** `Flaky Test` — 코드를 안 고쳤는데도 통과했다 실패했다 하는 들쭉날쭉한 시험. 방치하면 실패를 다 무시하게 되어 시험 전체가 무력해진다.
- **테스트 주도 개발** `Test-Driven Development, TDD` — 시험을 먼저 적고 그것을 통과하게 코드를 적는 방식. 무엇을 만들지 먼저 정하게 만드는 효과가 크다.

### 남의 코드를 가져다 쓰기

- **빌드** `Build` — 소스 코드와 필요한 것들을 모아 실행 가능한 물건으로 만드는 과정. <sub>관련어 의존성, 잠금 파일, 아티팩트, 재현 가능한 빌드</sub>

#### 의존성

<sub>Dependency</sub>

**내 코드가 돌기 위해 필요한 남의 코드.**

<sub>관련어 잠금 파일, 패키지 관리자, 시맨틱 버전(0장), 공급망 공격(47장에서 다룬다)</sub>

- **패키지 관리자** `Package Manager` — 의존성을 내려받고 버전을 맞춰 주는 도구. 언어마다 따로 있다.
- **잠금 파일** `Lock File` — 실제로 설치된 버전을 정확히 적어 둔 파일. 이것을 같이 기록해야 남의 기계에서도 같은 것이 깔린다.
- **아티팩트** `Artifact` — 빌드가 만들어 낸 결과물. 실행 파일, 컨테이너 이미지, 패키지 같은 것들이다.
- **재현 가능한 빌드** `Reproducible Build` — 같은 소스에서 언제 돌려도 비트 단위로 같은 결과가 나오는 빌드. 시각과 경로 같은 것이 섞여 들어가면 깨진다.
- **모노레포** `Monorepo` 〔유동〕 — 여러 프로젝트를 저장소 하나에 담는 방식. 함께 바꾸기 쉽고 저장소가 커진다. 어디까지를 하나로 볼지가 조직마다 다르다.

### 자동으로 검사하고 내보내기

#### CI/CD

<sub>Continuous Integration / Continuous Delivery</sub>

**코드를 올릴 때마다 자동으로 빌드하고 검사하고, 통과하면 자동으로 내보내는 절차.**

갈리는 자리 — 뒤의 D를 배포 준비까지 (Continuous Delivery)로 보는 쪽과 사람 손 없는 실제 배포까지 (Continuous Deployment)로 보는 쪽이 갈린다

<sub>관련어 파이프라인, 카나리, 롤백 (배포), 스테이징</sub>

- **파이프라인 (CI)** `Pipeline` — 검사와 빌드와 배포 단계를 순서대로 엮어 놓은 흐름. 2장의 프로세서 파이프라인과 발상이 같다.
- **러너** `Runner` — 자동 검사를 실제로 돌리는 기계. 여기서 도는 것이 남의 코드라서 권한을 좁혀야 한다.
- **스테이징** `Staging` — 운영과 같은 모양으로 만들어 둔 시험 환경. 진짜와 다를수록 여기서 통과한 의미가 줄어든다.
- **카나리 배포** `Canary Deployment` — 새 버전을 일부 사용자에게만 먼저 보내고 지켜보는 방식. 이름은 탄광의 카나리아에서 왔다.
- **블루 그린 배포** `Blue-Green Deployment` — 같은 규모의 환경 둘을 두고 통째로 바꿔 치는 방식. 되돌리기가 빠르고 자원이 두 배 든다.
- **롤백 (배포)** `Rollback` — 내보낸 것에 문제가 생겼을 때 이전 버전으로 되돌리는 일. 5장의 트랜잭션 롤백과 이름만 같다.
- **배포 빈도** `Deployment Frequency` — 얼마나 자주 내보내는지. 되돌리는 데 걸리는 시간과 같이 봐야 뜻이 생긴다.

### 적을 때 도와주는 것들

- **린터** `Linter` — 문법은 맞지만 문제가 될 만한 코드를 찾아 주는 도구. 규칙을 팀이 정해 둔다.
- **포매터** `Formatter` — 줄 맞춤과 띄어쓰기를 자동으로 통일하는 도구. 이 논쟁을 아예 없애 버리는 것이 목적이다.
- **정적 분석** `Static Analysis` — 코드를 돌리지 않고 읽어서 문제를 찾는 일. 타입 검사와 보안 검사가 여기 속한다.
- **디버거** `Debugger` — 프로그램을 중간에 멈추고 값을 들여다보는 도구. 찍어 보는 것보다 빠른 경우가 많다.
- **프로파일러** `Profiler` — 어디서 시간을 쓰는지 재는 도구. 짐작으로 최적화하지 않게 해 준다.
- **IDE** `Integrated Development Environment` — 편집과 빌드와 디버깅을 한자리에서 하는 도구. 코드 생성 기능이 여기 붙으면서 성격이 바뀌는 중이다.
- **언어 서버** `Language Server, LSP` — 편집기에 코드 정보를 알려 주는 별도 프로그램. 편집기와 언어를 따로 만들 수 있게 한 규약이다. 39장에서 에이전트가 이 정보를 쓰기도 한다.
- **문서화** `Documentation` — 무엇이 왜 이렇게 되어 있는지 적어 두는 일. 코드 옆에 두면 같이 낡고, 멀리 두면 안 읽힌다.
- **체인지로그** `Changelog` — 버전마다 무엇이 바뀌었는지 적은 목록. 특히 깨는 변경을 여기서 알린다.

## 자주 헷갈리는 짝

- **병합과 리베이스** 같은 점은 둘 다 갈래를 합친다는 것.
다른 점은 기록의 모양이다. 병합은 갈라진 흔적을 남기고 리베이스는 한 줄로 편다.
- **커밋 (git)과 커밋 (DB)** 같은 점은 둘 다 확정한다는 뜻이라는 것.
다른 점은 되돌리는 방법이다. 앞은 새 커밋으로 되돌리고 뒤는 롤백으로 없앤다.
- **단위 테스트와 통합 테스트** 같은 점은 둘 다 자동 검사라는 것.
다른 점은 진짜를 얼마나 쓰는가다. 진짜에 가까울수록 느리고 잘 깨진다.
- **CI와 CD** 같은 점은 둘 다 자동화된 절차라는 것.
다른 점은 앞이 합치기 전이고 뒤가 합친 뒤라는 것.
- **스테이징과 카나리** 같은 점은 둘 다 위험을 줄이려는 장치라는 것.
다른 점은 진짜 사용자가 있는가다. 카나리에는 있다.

## 지금 움직이는 것

코드 생성 도구가 들어오면서 이 절차의 무게중심이 옮겨 가고 있다. 적는 시간이 줄고 검토하는 시간이 늘었다. 그래서 리뷰의 부담과 테스트의 값이 같이 올라갔고, 변경 크기를 작게 유지하는 규율이 예전보다 더 중요해졌다. 39장에서 이 변화를 다시 다룬다.

## 더 볼 곳

여기서 나온 빌드 결과물이 8장에서 컨테이너 이미지가 된다. 의존성 문제는 47장에서 공급망 공격으로 돌아오고, 테스트 층 구조는 42장에서 모델 평가로 옮겨 간다.
